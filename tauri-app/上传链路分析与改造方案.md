# 桌宠文件上传：现状分析与改造方案

> 环境：虚拟机 192.168.1.234（WeKnora v0.9.0，API `http://192.168.1.234:18080`）
> 验证时间：2026-11-05 15:10–15:20
> 验证方式：用真实 access token 调接口，创建了两个探针知识库上传测试文件，验证完已删除

> **状态：已实现，随 v0.8.13 发布。** 落地时实测到两处与本文原判断不同，已按实测修正：
> 1. 重复文件返回的是 **HTTP 409**（不是 200），且 `success=false` —— 必须先按 `code=duplicate_file` 判定，
>    否则「库里已有」会被显示成「失败」。
> 2. `POST /auth/refresh` 的响应是**扁平 snake_case**：`{success, access_token, refresh_token}`，
>    不是包在 `data` 里的 camelCase；且刷新令牌一次性，用后旧令牌立即作废。
>
> 实现位置：`src-tauri/src/upload.rs`（队列/上传/轮询/令牌）+ `tauri-bridge.js`（仅转发）。

---

## 一、一句话结论

桌宠的「上传」**从来没有发过一个 HTTP 请求**：`tauri-bridge.js` 里的 `uploadPaths` 是 `setTimeout` 模拟，
所以文件不会进知识库；而「0/1 已处理」的气泡，是这条模拟流水线在**被隐藏的面板窗口**里跑定时器，
窗口一隐藏，定时器停摆 + 气泡文案是粘性的（`say(text, 0)` 永不自动消失），于是一直停在 0/1。

## 二、后端真实契约（实测）

### 2.1 鉴权

| 项 | 值 |
|---|---|
| 登录 | `POST /api/v1/auth/login` `{email, password}` → `data.token` |
| 请求头 | `Authorization: Bearer <token>` + `X-Tenant-ID: <tenant_id>` |
| access token 有效期 | 1 天（实测 exp - iat = 86400s） |
| refresh token | 7 天，`POST /api/v1/auth/refresh` |

不带 `X-Tenant-ID` 或 token 缺失 → `401 {"error":"Unauthorized: missing authentication"}`。

### 2.2 上传

```
POST /api/v1/knowledge-bases/{kb_id}/knowledge/file
Content-Type: multipart/form-data
字段：file（唯一必需字段；可带 tag_ids / process_config）
```

成功返回（HTTP 200）：

```json
{
  "success": true,
  "data": {
    "id": "f8144eff-ce97-4fe0-a142-c4a60d97f175",
    "knowledge_base_id": "3afd42f8-...",
    "title": "probe4.md",
    "type": "file",
    "file_name": "probe4.md",
    "file_type": "md",
    "file_size": 43,
    "file_hash": "da8ad9f6...",
    "file_path": "resource://MGLd2FP-2BqXXVIDKD0VOw",
    "parse_status": "pending",
    "enable_status": "disabled",
    "embedding_model_id": "builtin-embedding-jina",
    "created_at": "2026-11-05T15:15:52+08:00"
  }
}
```

**重复上传**（同一 KB、同一 file_hash）返回 HTTP 200，但响应体是**错误码结构**，不是 `success:true`：

```json
{ "code": "duplicate_file", "data": { /* 已存在的那条记录，含 id 和当前 parse_status */ } }
```

客户端必须识别 `code === 'duplicate_file'`，把状态置成「已存在」并复用返回的 `id`。

### 2.3 解析状态流转（实测时序）

| 时间 | parse_status | enable_status |
|---|---|---|
| t+0s | `pending` | `disabled` |
| t+3s 内 | `processing` | `disabled` |
| t+10s | `finalizing` | `enabled` |
| t+20s | `completed` | `enabled` |

失败样本（KB 未配向量模型时）：

```json
{ "parse_status": "failed",
  "error_message": "failed to get embedding model: model ID cannot be empty" }
```

### 2.4 查询

| 用途 | 接口 | 响应结构 |
|---|---|---|
| 单条状态 | `GET /api/v1/knowledge/{id}` | `{data:{...}}` |
| 库内列表 | `GET /api/v1/knowledge-bases/{kb}/knowledge?page=1&page_size=20` | `{data:[...]}`（**数组**，不是分页对象） |
| 删除 | `DELETE /api/v1/knowledge-bases/{kb}` | 200 |

### 2.5 限制

| 项 | 值 |
|---|---|
| 单文件上限 | `MAX_FILE_SIZE_MB=50` |
| 存储 | local，`/data/files`（容器内） |
| 类型白名单 | `STORAGE_ALLOW_LIST=`（空 = 未启用白名单） |

## 三、现状根因

### 3.1 上传是假的

`tauri-app/src/public/js/tauri-bridge.js:670`

```js
uploadPaths: async (paths) => {
  ...
  uploadQueue.push(item);
  notifyUploadUpdate(item);
  setTimeout(() => { item.status = 'uploading'; ... }, 500);
  setTimeout(() => { item.status = 'done'; ... }, 1500);   // 1.5 秒后自己宣布成功
}
```

全程没有 `fetch` / 没有 `knowledgeId` / 没有 `file_path`。所以面板里所有「已入库」都是假的，
后端 `knowledges` 表里没有对应记录。

### 3.2 状态机跑在会被隐藏的窗口里 → 气泡卡在 0/1

- 队列 `uploadQueue` 是模块级数组，**每个窗口一份**（桌宠窗口、面板窗口互不相通）；
- 推进状态的是这个窗口里的 `setTimeout`；
- 面板被隐藏后，WKWebView 会降频/挂起定时器，状态不再推进；
- 桌宠只是通过 `upload:update` 订阅，它收到的最后一条就是 `queued`（0/1）；
- 气泡文案是粘性的：`pet.js:360` `say(`${done}/${total} 已处理`, 0)`，duration=0 = 永不自动消失。

三个条件凑齐，桌宠就永远停在「0/1 已处理」。

### 3.3 其它已埋好的半成品

- 面板 `STATUS_TEXT` 已经预留了 `queued/uploading/parsing/done/exists/failed`，但没有任何代码写入真实的 `parsing/exists`；
- `renderQueue` 已经会渲染 `knowledgeId` 存在时的「移除」按钮（真实接口才会给这个字段）；
- `retryUpload`、`clearUploads`、`listUploads` 都已有前端壳子，只是桥接层全是假的。

也就是说：**只差把桥接层换成真实实现，UI 基本不用重做。**

### 3.4 token 没有刷新机制

`apiRequest` 只用 `cfg.token`，没有 `refresh` 逻辑。access token 1 天过期后，
上传/问答都会 401，表现为「点了没反应」。

## 四、改造方案

### 4.1 总体思路：上传下沉到 Rust，渲染层只订阅

理由：文件字节根本不需要进 JS（避免 50MB 读进内存），且 Rust 侧状态不受窗口隐藏/重开影响。

### 4.2 Rust 侧

`src-tauri/Cargo.toml`：

```toml
tauri-plugin-http = { version = "2", features = ["multipart"] }   # reqwest 已被 re-export
```

新增 `src-tauri/src/upload.rs`：

```rust
struct QueueItem {
    id: String, path: String, name: String, size: u64,
    status: String,        // queued | uploading | parsing | done | exists | failed
    knowledge_id: Option<String>,
    parse_status: Option<String>,
    error: Option<String>,
    progress: f32,
}

#[tauri::command]
async fn upload_files(
    app: AppHandle, state: State<'_, UploadState>,
    server_url: String, token: String, tenant_id: i64,
    kb_id: String, paths: Vec<String>,
) -> Result<UploadResult, String>
```

要点：

1. **读文件用 `std::fs::File` + `reqwest::Body::from(file)` 流式上传**，不整读进内存；
2. multipart 只放 `file` 字段，文件名用真实文件名，MIME 按扩展名推断；
3. 大小超 50MB 直接判定 `failed`，不发请求；
4. 响应解析三态：
   - `success === true` → 取 `data.id`，进入解析轮询
   - `code === 'duplicate_file'` → `status='exists'`，复用 `data.id`
   - 其它 → `status='failed'`，`error` 取 `error.message` / `message`
5. 解析轮询：`GET /api/v1/knowledge/{id}`，间隔 2s，最长 10 分钟；
   `completed` → `done`；`failed` → `failed` + `error_message`；
6. 每次状态变化 `app.emit("upload:update", { item, stats })` —— **沿用现有事件名和 payload 形状**，
   前端 `onUploadUpdate` 一行都不用改；
7. 队列放 `tauri::State<Mutex<Vec<QueueItem>>>`，`list_uploads` 直接返回它；
8. 401 单独返回错误码，前端提示重新登录。

### 4.3 前端侧

`tauri-bridge.js`：

```js
uploadPaths: async (paths) => invoke('upload_files', { serverUrl, token, tenantId, kbId, paths }),
listUploads: async () => invoke('list_uploads') || [],
clearUploads: async () => invoke('clear_uploads'),
retryUpload: async (id) => invoke('retry_upload', { id }),
deleteKnowledge: async (kid) => invoke('delete_knowledge', { knowledgeId: kid }),
```

`pet.js` 气泡（改 3 处）：

- 文案分阶段：`上传中 1/3` → `解析中 2/3` → `已入库 3/3`；
- 加兜底：60s 无状态变化 → `上传好像卡住了，点我看详情`，并清掉粘性气泡；
- `say(..., 0)` 只在上传进行中使用，结束必须走 `hideBubble()`。

`panel.js` 状态映射补齐：

| 后端 | 客户端 status | 文案 |
|---|---|---|
| 刚上传完 `pending` | `parsing` | 排队解析 |
| `processing` | `parsing` | 解析中 |
| `finalizing` | `parsing` | 整理中 |
| `completed` | `done` | 已入库 |
| `failed` | `failed` | 失败 · `error_message` |
| `duplicate_file` | `exists` | 已存在 |

### 4.4 顺带要修的边界

1. **知识库必须配向量模型**：实测未配时每条上传都会 `failed`，错误是
   `failed to get embedding model: model ID cannot be empty`。
   面板选择/创建库时要校验 `embedding_model_id` 非空，失败时把后端 `error_message` 原样显示。
2. **token 刷新**：401 时用 refresh token 换新 access token，失败才弹登录。
3. **重复文件**：识别 `duplicate_file`，显示「已存在」，不要当失败重试。

## 五、验收标准

1. 拖 1 个 md 到桌宠 → 面板「存入」→ 队列 `上传中 → 解析中 → 已入库`，15 秒内完成；
2. 完成后的 `knowledge_id` 在 Web 端知识库列表里能查到同一篇；
3. 关掉面板、重启 App，队列状态仍在（来自 Rust）；
4. 拖同一个文件第二次 → 显示「已存在」，不产生第二条记录；
5. 拖 60MB 文件 → 前端直接拒绝，不发请求；
6. 目标库没配向量模型 → 队列显示失败原因，而不是卡在 0/1。
