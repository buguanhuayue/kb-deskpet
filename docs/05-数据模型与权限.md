# 05 · 数据模型与权限

> 面向：开发、DBA。核心是第三节——**权限判定逻辑是全系统最不能改错的地方**。

## 一、实体关系

```
departments ──┬──< users
              │
              └──< documents ──┬──< chunks
                               ├──< acl
                               └──< jobs

audit_logs（独立，当前代码未写入）
```

## 二、表结构

### departments

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `name` | text UNIQUE | 部门名 |
| `parent_id` | uuid FK→self | 支持树形，**当前代码未用到层级逻辑** |

### users

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `email` | text UNIQUE | 登录名 |
| `name` | text | 显示名 |
| `password_hash` | text | **P0 未使用**，为接 SSO/密码登录预留 |
| `api_token` | text UNIQUE | Bearer Token，接 SSO 后置空 |
| `dept_id` | uuid FK | 为 `NULL` 时**不能入库**，提问也基本查不到东西 |
| `role` | text | `member` / `editor` / `admin`，**当前代码未按 role 做任何鉴权** |

> `role` 目前只是标记，没有权限含义。任何登录用户都能上传、提问。若需要"只有 editor 能传"，
> 需在路由层加判断——当前没有。

### documents

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `title` | text | 显示标题 |
| `source_type` | text | `text` / `file` / `video` / `image`（后两者未实现） |
| `dept_id` | uuid FK NOT NULL | 归属部门，**权限判定依据** |
| `owner_id` | uuid FK NOT NULL | 上传者 |
| `status` | text | 状态机，见第五节 |
| `storage_path` | text | 原文件落盘路径（容器内） |
| `mime` / `bytes` / `sha256` | | 文件元信息，`sha256` 用于去重 |
| `version` | int | 预留，当前恒为 1 |
| `visibility` | text | `private` / `dept` / `company` |
| `ext` | jsonb | 扩展信息。纯文本存 `{"content": "..."}`；降级时带 `embed_degraded: true` |
| `chunk_count` | int | 切片数，`ready` 后写入 |
| `error_code` / `error_msg` | text | 失败原因 |
| `published_at` | timestamptz | 预留，当前未用 |
| **唯一约束** | `UNIQUE (dept_id, sha256)` | 同部门同内容去重的依据 |

### chunks（检索的核心表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `doc_id` | uuid FK CASCADE | 删文档级联删切片 |
| `dept_id` | uuid NOT NULL | **冗余自 documents**，为了检索时少一次 JOIN |
| `seq` | int | 文档内序号，从 0 开始 |
| `text` | text | 切片正文 |
| `locator` | jsonb | `{"page": n}` 或 `{"start": a, "end": b}` |
| `token_count` | int | 字符数（非严格 token） |
| `embedding` | **vector(1024)** | 向量，可为 `NULL`（降级模式） |
| `embed_model` | text NOT NULL | 生成该向量的模型名；降级时为 `none` |
| `tsv` | tsvector | 中文经 jieba 预分词后写入 |
| **唯一约束** | `UNIQUE (doc_id, seq)` | 保证重跑幂等 |

索引：

| 索引 | 类型 | 用途 |
|---|---|---|
| `idx_chunks_tsv` | GIN | 关键词检索 |
| `idx_chunks_hnsw` | HNSW `m=16, ef_construction=64` | 向量检索（余弦） |
| `idx_chunks_dept` | B-tree | 部门过滤 |

### jobs（任务队列）

| 字段 | 说明 |
|---|---|
| `doc_id` / `kind` | 目标任务，`kind` 当前只有 `ingest` |
| `status` | `queued` / `running` / `done` / `failed` |
| `attempts` | 已尝试次数，每次抢占 +1 |
| `run_after` | 可执行时间，支持延迟重试 |
| `locked_at` | 抢占时间 |

队列靠 `claim_job()` 函数原子抢占：

```sql
UPDATE jobs SET status='running', locked_at=now(), attempts=attempts+1
WHERE id = (SELECT id FROM jobs WHERE status='queued' AND run_after<=now()
            ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;
```

`SKIP LOCKED` 保证多 worker 不抢同一条。**函数必须是 `RETURNS SETOF jobs`**——
`0001` 里写的是 `RETURNS jobs`，空队列时会返回"一行全 NULL"，导致 worker 把
`doc_id='None'` 当真任务疯狂重试。`0002` 已修。

### acl（显式授权）

| 字段 | 说明 |
|---|---|
| `doc_id` | 被授权文档 |
| `subject_type` | `user` 或 `dept` |
| `subject_id` | 用户或部门 ID |
| `permission` | 当前只用 `read` |

用于"这份文档额外给某个部门看"这类需求。**当前没有任何接口写这张表**，需手工插入。

## 三、权限判定（全系统最关键的一段）

唯一的权限定义在 `server/app/search/sql.py` 的 `ACL` 常量里，**只此一处**：

```sql
(
      d.visibility = 'company'
   OR d.owner_id = %(uid)s::uuid
   OR (d.visibility = 'dept' AND %(dept)s::uuid IS NOT NULL AND c.dept_id = %(dept)s::uuid)
   OR EXISTS (
        SELECT 1 FROM acl a
        WHERE a.doc_id = c.doc_id
          AND ((a.subject_type = 'user' AND a.subject_id = %(uid)s::uuid)
            OR (a.subject_type = 'dept' AND a.subject_id = %(dept)s::uuid))
      )
)
```

四选一，满足其一即可见：

| 条件 | 含义 |
|---|---|
| `visibility = 'company'` | 全公司公开 |
| `owner_id = 当前用户` | **自己传的，永远可见**（包括设成 private 的） |
| `visibility = 'dept'` 且同部门 | 部门内共享 |
| `acl` 表里有匹配记录 | 显式授权 |

### 三条铁律（违反会导致越权或漏数据）

1. **权限必须写在 SQL 的 `WHERE` 里**，不允许"先查 40 条再在 Python 里过滤"。
   否则 `LIMIT 40` 可能把别人的 40 条全取回来，过滤完变成 0 条——既不安全也不好用。
2. **两路召回（向量 / 关键词）都必须带同一个 `ACL`**。少写一处，那一路就漏权限。
3. **改 `ACL` 常量等于改整个系统的权限模型**。改完必须重新验四类可见性 × 三种身份
   的组合（见 [07-验收标准](07-验收标准.md#三权限验收必测项当前完全未测)）。

### 已知的权限缺口

| 问题 | 影响 | 状态 |
|---|---|---|
| `GET /api/documents/{doc_id}` 未做权限过滤 | 知道 doc_id 就能看元信息（不含正文） | 待修 |
| `role` 字段无实际作用 | 任何用户都能上传 | 待明确需求 |

## 四、向量维度不可随意更改

`chunks.embedding` 是 `vector(1024)`，**硬编码在 DDL 里**。

- 换成 768 维或 1536 维的模型 → 插入时直接报错
- 已入库的向量与新模型不兼容（不同模型的向量空间不可比）

**换模型的正规流程**：

```sql
-- 1. 清空旧向量（不是删文档，文档本身还在）
UPDATE chunks SET embedding = NULL, embed_model = 'pending';
-- 2. 改 .env 的 EMBED_MODEL / EMBED_DIM，并改 DDL（如需改维度）
-- 3. 重建 embed 容器
docker compose up -d --build embed
-- 4. 把相关文档重新入库（重新上传，或手工把 jobs 重置为 queued）
UPDATE jobs SET status='queued', attempts=0, error=NULL WHERE status='failed';
```

> 只要维度相同（比如从 `jina-embeddings-v3` 换到别的 1024 维模型），
> **旧向量仍可用但质量会劣化**——不同模型空间不同，混用等于用两把不同的尺子量距离。
> 严格做法是全部重算。

## 五、文档状态机

```
uploaded ──► parsing ──► chunking ──► embedding ──► ready
    │           │           │            │
    └───────────┴───────────┴────────────┴──────► failed
                                                  （error_code + error_msg）
```

| 状态 | 含义 | 卡在这里怎么办 |
|---|---|---|
| `uploaded` | 已落盘待处理 | worker 没跑 / 队列堵塞 |
| `parsing` | 解析中 | 文件损坏，看 `error_msg` |
| `chunking` | 切片中 | 抽取为空（扫描件） |
| `embedding` | 向量化中 | 模型服务不可达，看 embed 日志 |
| `ready` | 可检索 | 正常 |
| `failed` | 失败 | 看 `error_code` / `error_msg` |

只有 `status='ready'` 的文档参与检索（两路 SQL 都有 `WHERE d.status = 'ready'`）。

## 六、常用运维 SQL

```bash
# 进 psql
docker compose exec postgres psql -U kb -d kb
```

```sql
-- 看所有文档状态
SELECT id, title, status, chunk_count, left(coalesce(error_msg,''),60) AS err
FROM documents ORDER BY created_at DESC LIMIT 20;

-- 看卡住的任务
SELECT id, doc_id, status, attempts, run_after, error
FROM jobs WHERE status <> 'done' ORDER BY created_at DESC;

-- 重跑失败任务
UPDATE jobs SET status='queued', attempts=0, error=NULL, run_after=now()
WHERE status='failed';

-- 把某篇文档重新入库（等价于手工重置）
UPDATE documents SET status='uploaded', chunk_count=0, error_code=NULL, error_msg=NULL
WHERE id='<doc_id>';
UPDATE jobs SET status='queued', attempts=0, error=NULL WHERE doc_id='<doc_id>';
DELETE FROM chunks WHERE doc_id='<doc_id>';

-- 向量覆盖情况（健康度核心指标）
SELECT count(*) AS total,
       count(embedding) AS with_vec,
       count(DISTINCT embed_model) AS models
FROM chunks;

-- 各文档切片数分布（判断切片是否合理）
SELECT d.title, count(c.id) AS chunks, round(avg(length(c.text))) AS avg_len
FROM documents d LEFT JOIN chunks c ON c.doc_id = d.id
GROUP BY d.id, d.title ORDER BY chunks DESC;

-- 给某部门额外授权一份文档
INSERT INTO acl (doc_id, subject_type, subject_id)
VALUES ('<doc_id>', 'dept', '<dept_id>') ON CONFLICT DO NOTHING;

-- 新建用户并签发 token
INSERT INTO users (name, email, api_token, dept_id, role)
VALUES ('张三', 'zhangsan@corp', encode(gen_random_bytes(24),'hex'), '<dept_id>', 'member');

-- 删除一篇文档（级联删切片与任务）
DELETE FROM documents WHERE id = '<doc_id>';
```

## 七、数据生命周期

| 数据 | 位置 | 备份方式 | 丢失后果 |
|---|---|---|---|
| 文档元信息、切片、向量 | docker 卷 `pgdata` | `pg_dump` | 全丢，需重新入库 |
| 原始文件 | docker 卷 `filedata` | 卷备份或 `STORAGE_DIR` 拷贝 | 原文丢，无法核对引用 |
| 模型权重 | docker 卷 `models` | **无需备份**，可重新下载 | 重新下载 3.2 GB |
| 配置密钥 | `.env` | 单独保管 | 需重新签发 |

> 关键：`pgdata` 和 `filedata` **必须一起备份**。只备数据库会导致引用点开是空文件；
> 只备文件则检索全废。
