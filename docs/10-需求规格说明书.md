# 10 · 需求规格说明书（SRS）

> 面向：甲方业务负责人、项目负责人、开发、测试。
> 用途：把"要做什么"固化成可编号、可验收、可追溯的条目。后续所有设计、代码、测试都回到这里的编号上。
>
> 版本：v1.0 ｜ 最后更新：2026-10-31 ｜ 状态：已冻结（变更走第十一节）

## 一、文档目的与范围

本文定义 **kb-deskpet P0 文本闭环** 的需求基线，覆盖：

- 文档上传 → 解析 → 切片 → 向量化 → 入库
- 混合检索 → 重排 → 拒答判定 → 带引用生成
- 部门级权限、鉴权、健康检查、部署运维

**不覆盖**：桌宠客户端交互、视频/音频入库、OCR、SSO、多轮对话。这些在第九节明确列为范围外，
不是"漏了"，是"这一期不做"。

## 二、业务背景与问题定义

一句话：**公司文档找得到、说得清、不乱说。**

三条现状痛点（详见 [01-业务场景与能力边界](01-业务场景与能力边界.md)）：

| # | 痛点 | 现有手段为什么不行 | 本系统的对策 |
|---|---|---|---|
| P1 | 文档散落在 OA / 网盘 / 群里 | 没有统一入口 | P0 只承接"传进来之后"，散的问题靠流程 |
| P2 | 关键词搜不到（术语不一致） | 字面匹配，"住宿费"搜不到"差旅标准" | 语义向量 + 关键词双路召回 |
| P3 | 通用 AI 会编 | 模型用参数记忆补全，无法核对 | 严格拒答 + 页码级引用 |

**需求边界的关键判断**：本系统是"**有据可查的问询台**"，不是"会聊天的专家"。
所有需求都服从这条定位——宁可说"查不到"，不可给一个无法核对的答案。

## 三、干系人

| 干系人 | 角色 | 关心什么 | 在需求中的话语权 |
|---|---|---|---|
| 公司管理层 | 出资方 | 数据不出内网、成本可控、能不能真用起来 | 决定范围与优先级 |
| 普通员工 | 主要用户 | 问一句话能不能得到能核对的答案 | 决定可用性需求 |
| 部门管理员 | 资料 owner | 本部门文档不被别的部门看到 | 决定权限需求（一票否决） |
| IT / 运维 | 运行方 | 挂了知不知道、数据丢不丢、怎么备份 | 决定非功能需求 |
| 实施 / FDE | 交付方 | 能不能在一个工作日内装起来、能不能验收 | 决定部署与文档需求 |

## 四、优先级方法

采用 **MoSCoW + P 级双标**，避免"都很重要"导致范围失控：

| 级别 | 含义 | 判定规则 |
|---|---|---|
| **P0 / Must** | 缺了系统不成立 | 缺它则"上传→检索→引用→拒答"闭环断链，或存在越权/丢数据风险 |
| **P1 / Should** | 影响可用性但有替代路径 | 例如没有删除接口时可走 SQL；没有 SSO 时可发 Token |
| **P2 / Could** | 体验增强 | 没有它业务照跑 |
| **Won't** | 本期明确不做 | 写进第九节，避免反复讨论 |

**P0 的判定不看工作量，只看断链风险。** 权限属于 P0，因为一次越权就是事故；
前端美化属于 P2，因为验收台够用。

## 八、约束与假设

**技术约束**

1. 部署在企业内网单机，不假设有 K8s、对象存储、Redis。
2. 数据库必须是 PostgreSQL（向量与全文检索同库，减少一个组件）。
3. 向量维度锁 1024，换模型必须全量重跑（见 [12-系统设计](12-系统设计说明书.md) ADR-02）。
4. 生成模型走 OpenAI 兼容协议，允许换供应商。

**业务假设**

1. 文档由员工手工上传，系统不做爬取/同步。
2. 用户已有公司身份，P0 用预发 Token 代替 SSO。
3. 单部门文档量在千级、切片在十万级以内（HNSW 单机足够）。
4. 允许"查不到"，但不允许"编"——这是验收的底线。

**明确放弃的假设**

- ❌ 不假设文档排版规范（PDF 可能是双栏、表格、页眉页脚干扰）。
- ❌ 不假设用户会正确使用术语（这正是需要语义检索的原因）。
