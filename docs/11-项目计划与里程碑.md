# 11 · 项目计划与里程碑

> 面向：项目负责人、甲方对接人、实施工程师。
> 用途：说明这件事怎么被拆开、按什么顺序做、每个节点怎么算"过了"，以及哪些风险会掀桌子。
>
> 版本：v1.0 ｜ 编制：2026-10-30 ｜ 修订：2026-10-31

## 一、项目目标与成功判据

**交付目标**：在一台内网 Ubuntu 虚拟机上，跑通"上传文档 → 提问 → 带页码引用作答 → 查不到就拒答"的完整闭环，
并交付可复现的部署脚本与全套文档。

**成功判据（三层，缺一层都不算成功）**

| 层 | 判据 | 判定方式 | 当前 |
|---|---|---|---|
| 技术 | F1–F13 全绿，N1/N2/N5 达标 | [07-验收标准](07-验收标准.md) 实测 | ✅ 达成 |
| 业务 | ≥20 篇真实文档、30 题评测、recall@5 ≥ 85%、拒答 ≥ 95%、权限 P1–P7 通过 | 同上 | ❌ 未开始 |
| 运营 | 运维能独立巡检/备份/恢复，用户不需要培训就会用 | 交接演练 + 使用手册 | ⚠️ 文档就绪，未演练 |

> **口径统一**：当前只能对外说"技术验证通过"，不能说"上线"。这不是措辞问题，
> 是因为业务层六项判据一项都没做。

## 二、工作分解（WBS）

```
1 需求与方案
  1.1 场景与痛点确认            1.2 能力边界划定（做什么/不做什么）
  1.3 技术选型与替代方案对比      1.4 交付物清单确认

2 骨架实现（可运行的闭环）
  2.1 数据库 schema 与迁移       2.2 上传/解析/切片
  2.3 向量化与关键词索引         2.4 混合检索与重排
  2.5 拒答闸门与带引用生成       2.6 验收台单页

3 环境与部署
  3.1 目标机基线（Docker/镜像源/时区）  3.2 compose 四容器编排
  3.3 打包/引导脚本              3.4 首次真实迁移与纠偏

4 依赖治理（本期最大变数）
  4.1 向量服务可用性评估          4.2 本地 embed 服务（C 方案）
  4.3 重排本地化与降级            4.4 端口与密钥配置

5 验证
  5.1 功能自测（9 端点）          5.2 端到端问答与拒答
  5.3 稳定性（重启自愈/长跑）      5.4 权限多部门测试（未做）
  5.5 评测集扩充到 30 题（未做）

6 交付
  6.1 交付文档包                  6.2 验收标准与记录
  6.3 复盘与移交清单              6.4 甲方签收（未做）
```

## 三、里程碑

| 里程碑 | 计划日期 | 交付物 | 出口准则（Gate） | 实际 |
|---|---|---|---|---|
| **M0 方案冻结** | 10-30 12:00 | 范围、技术选型、P0 清单 | 甲方确认"不做 OCR/视频/多轮" | ✅ 10-30 |
| **M1 本地闭环跑通** | 10-30 17:00 | 可上传、可检索、可作答的代码 | 本机 `docker compose up` 后能完成一次带引用问答 | ✅ 10-30 16:31（`5024d44`） |
| **M2 目标机可运行** | 10-30 18:00 | 迁移脚本 + 目标机实例 | 局域网 `http://192.168.1.234:9527` 可访问并作答 | ✅ 10-30 18:09（`4d7c860`） |
| **M3 稳定性达标** | 10-30 19:00 | 端口 9527、降级开关、队列修复 | Docker 重启后 20 s 自愈；空队列 worker 不崩 | ✅ 10-30 18:21（`c4125db`） |
| **M4 去外部依赖** | 10-31 09:00 | 本地 embed + rerank（C 方案） | 断掉云端向量服务后仍可入库与检索，维度不变 | ✅ 10-31 08:50（`c5766cb`） |
| **M5 文档交付** | 10-31 12:00 | 全生命周期文档包 + 验收标准 | 文档可让陌生人独立部署；索引完整 | ✅ 10-31 09:11（`53effe6`）+ 本轮补齐 |
| **M6 业务验收** | 待甲方排期 | 真实文档接入、30 题评测、权限实测 | [07](07-验收标准.md) 第八节"业务验收"六项全绿 | ❌ 未开始 |

**关键路径**：M1 → M2 → M3 → M4 → M5。M6 不在开发关键路径上，但在"能不能用"的关键路径上。

## 四、排期与实际耗时

实际执行是两天连续推进（非理想排期，是真实记录）：

```
10-30
09:00 ─┬─ 需求澄清、能力边界、选型        (2.0h)
       ├─ 骨架：schema/上传/切片/检索/生成 (3.0h)  → M1
14:00 ─┼─ 打包迁移、目标机基线、首次部署    (2.5h)  → M2
17:00 ─┼─ 端口/降级/队列修复、复测          (1.5h)  → M3
10-31
08:00 ─┼─ 本地 embed + rerank 落地与验证   (2.0h)  → M4
09:00 ─┴─ 文档包 + 本轮生命周期文档补齐    (3.0h)  → M5
```

| 工作包 | 计划 | 实际 | 偏差原因 |
|---|---|---|---|
| 需求与选型 | 2 h | 2 h | — |
| 骨架实现 | 4 h | 3 h | 范围收敛到 4 种格式、无前端框架 |
| 部署迁移 | 1.5 h | 2.5 h | 首次真实迁移暴露 3 个环境问题 |
| 依赖治理 | 0.5 h | 2 h | 云端余额耗尽，临时改 C 方案 |
| 文档 | 2 h | 3 h | 甲方追加全生命周期文档 |

**结论**：偏差集中在"环境"和"外部依赖"，不在业务逻辑。这两类偏差下次应在 M0 就预留缓冲。

## 六、依赖与关键路径

| 依赖 | 类型 | 风险 | 缓解 |

## 八、质量门禁

每个里程碑不允许"口头通过"，必须过闸：

| 门禁 | 时点 | 内容 | 不过怎么办 |
|---|---|---|---|
| G0 | 提交前 | 代码能起、无语法错误 | 不允许提交 |
| G1 | M1/M2 | `make check` 四项全绿 | 回退到上一提交 |
| G2 | M3 | Docker 重启自愈实测 | 不宣布"稳定" |
| G3 | M4 | 断开外部向量服务仍可检索 | 保留云端回退方案 |
| G4 | M5 | 文档能让陌生人照做部署 | 补文档，不放行 |
| G5 | M6 | [07](07-验收标准.md) 业务验收六项 | 不宣布上线 |

**回归最小集（每次改动必跑 6 条）**：健康检查、401、上传去重、检索命中、拒答、SSE 事件顺序。

## 九、沟通与变更管理

| 机制 | 频率 | 产出 |
|---|---|---|
| 每日进度同步 | 每日 | 昨日完成 / 今日计划 / 阻塞 |
| 里程碑评审 | 每个 M | 出口准则逐项打勾，不通过不进入下一阶段 |
| 变更单 | 按需 | 记录在 [10 §11](10-需求规格说明书.md)，同步改验收与测试 |
| 事故复盘 | 每次 P1 级故障 | 现象/根因/修复/防复发，进 [14 §4](14-实施记录与变更台账.md) |

**变更三原则**：
1. 改需求必须同时改验收口径与测试用例，否则视为未完成。
2. 临时方案必须写"何时必须还债"，否则永久化。
3. 任何"先上线再补"的决定必须由甲方书面确认，不接受口头。

## 十、计划 vs 实际偏差分析

| 偏差 | 事实 | 根因 | 下次怎么改 |
|---|---|---|---|
| C 方案临时插入 | 原计划用云端 embedding，余额耗尽后改为本地 | 选型时未核实账户余额与计费方式 | 选型必须附"可用性证据"（余额截图/压测） |
| 首次迁移踩 3 个坑 | 迁移目录、编码、compose stdin | 未在干净环境预演 | 迁移前必做一次"空机演练" |
| 文档返工 | 首版文档只覆盖交付，缺需求/规划/设计/实施 | 文档计划按"交付件"而非"生命周期"编排 | 文档 WBS 从第一天按阶段建目录 |
| 评测集没扩到 30 题 | 缺真实文档，出题无依据 | 业务输入未到位 | M6 前置条件写进合同/验收单 |

**一句话总结**：技术路径没走弯路，**流程性返工（环境、依赖、文档结构）占了大头**。
下一次同类项目，把这三块前置，整体工时可压到 1 天以内。
