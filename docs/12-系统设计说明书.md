# 12 · 系统设计说明书

> 面向：开发、架构评审、接手维护的人。
> 用途：解释系统**为什么这样搭**，而不只是"有哪些文件"。每个关键选择都有 ADR，每个失败路径都有降级。
>
> 版本：v1.0 ｜ 对应代码：`53effe6` ｜ 最后更新：2026-10-31

## 一、设计目标与原则

| 目标 | 设计手段 | 代价（明说） |
|---|---|---|
| 少组件、可单机跑 | 向量、全文、队列全放 PostgreSQL | 数据库是单点 |
| 权限不可能漏 | 权限谓词进 SQL，全系统只写一处 | 复杂授权需改 SQL，不是配置 |
| 答案可核对 | 切片不跨页，locator 必填 | 切片粒度受页边界限制 |
| 查不到就闭嘴 | 分数闸门在生成之前 | 阈值标定不好会误拒 |
| 换供应商不改代码 | 外部依赖全在 `services/` 一层 | 仍需改配置并重启 |
| 故障可降级 | 重排/向量失败均有回退路径 | 降级时质量下降且不易察觉 |

**核心原则**：**能用 30 行 SQL 解决的，不引入一个中间件。**
这不是技术保守，是因为这套系统要交给一个没有专职中间件运维的团队。

## 二、架构总览

```
                       ┌──────────────────────────────┐
   浏览器 / 验收台 ───▶ │  api  (FastAPI + uvicorn)    │ :8088 容器内
   curl / 集成方        │  /api/{health,me,documents,  │ 宿主机 9527
                       │        query,search,ingest}  │
                       └───────┬──────────────┬───────┘
                               │              │
                     SQL（含ACL）│              │ HTTPS（唯一出网）
                               ▼              ▼
                 ┌─────────────────────┐   ┌──────────────────┐
                 │ postgres:16 +       │   │ Agnes LLM API    │
                 │ pgvector 0.8.7      │   │ agnes-3.0-flash  │
                 │ 9 张表 / HNSW / GIN │   └──────────────────┘
                 └───────▲─────────────┘
                         │ claim_job() + 回写状态
                 ┌───────┴─────────────┐        ┌────────────────────────┐
                 │ worker（轮询 2s）    │───────▶│ embed 服务 :8088(容器) │
                 │ 解析→切片→向量化     │  HTTP  │ fastembed + onnxruntime│
                 └─────────────────────┘        │ /v1/embeddings         │
                                                │ /v1/rerank /health     │
                 ┌─────────────────────┐        │ 仅绑 127.0.0.1:8090    │
                 │ 卷 filedata（原文）  │        └────────────────────────┘
                 │ 卷 models（3.2GB）   │
                 └─────────────────────┘
```

**四个容器，三条数据通路**

| 通路 | 协议 | 说明 |
|---|---|---|
| api ↔ postgres | psycopg3 连接池 | 所有读写都带权限谓词 |
| api / worker ↔ embed | HTTP（OpenAI 兼容） | 向量化与重排，本地回环 |
| api ↔ LLM | HTTPS | 只发送拼好的 top-k 片段，不发全库 |

**为什么不画成微服务**：四个容器已经是"按部署单元拆"，不是按"组织架构拆"。
再拆只会增加网络故障面，不会增加能力。

## 三、模块划分

| 层 | 文件 | 职责 | 不允许做什么 |
|---|---|---|---|
| 入口 | `main.py` | 路由挂载、连接池生命周期、验收台 | 不放业务逻辑 |
| 鉴权 | `deps.py` | Bearer → `CurrentUser(uid, dept, role)` | 不做权限过滤（过滤在 SQL） |
| 接口 | `api/ingest.py` | 收文件/文本、算 sha256、建 doc + job | 不做解析 |
| 接口 | `api/query.py` | 检索、SSE 转发 | 不拼 SQL |
| 接口 | `api/meta.py` | 健康、当前用户、文档列表/详情 | 不返回他人文档 |
| 检索 | `search/tokenize.py` | jieba 分词、停用词、`to_tsquery` 拼接 | 不做 IO |
| 检索 | `search/sql.py` | **唯一的检索 SQL 与 ACL 谓词** | 不允许出现第二份 ACL |
| 检索 | `search/retrieve.py` | 双路召回 → RRF → 重排 → `Hit[]` | 不生成答案 |
| 检索 | `search/answer.py` | 闸门、上下文拼装、SSE、引用 | 不改检索结果顺序 |
| 入库 | `ingest/parsers/` | PDF 按页 / 文本按段 | 不切分块 |
| 入库 | `ingest/chunker.py` | 300–500 字切片、80 重叠、尾块合并 | 不跨页合并 |
| 入库 | `ingest/pipeline.py` | 状态机推进、写切片与向量、失败落错误码 | 不抢任务（抢任务在 worker） |
| 队列 | `worker.py` | `claim_job()` 轮询、异常兜底 | 不并发处理同一 doc |
| 外部 | `services/*` | embedding / rerank / llm / storage 的协议适配 | 不感知业务语义 |
| 模型 | `embed_service/app.py` | 加载 jina 模型，暴露 OpenAI 兼容接口 | 不做鉴权（只绑回环） |

**依赖方向**：`api → search/ingest → services → 外部`。反向依赖一律禁止，
所以换 LLM 供应商只动 `services/llm.py` 一个文件。

## 四、关键流程

### 4.1 上传入库

```
客户端                api                  postgres            worker              embed
  │  POST /ingest/file │                      │                  │                   │
  ├───────────────────▶│ 校验扩展名/大小      │                  │                   │
  │                    ├─ 流式落盘 + 边算 sha256 ────────────────▶│                   │
  │                    ├─ 查重 (dept_id, sha256) ────────────────▶│                   │
  │                    │   命中 → 直接返回 deduped:true + 原 id   │                   │
  │                    ├─ INSERT documents(status=uploaded) ─────▶│                   │
  │                    ├─ INSERT jobs(status=queued) ────────────▶│                   │
  │◀───────────────────┤ 202 {doc_id, deduped:false}              │                   │
  │                    │                      │   claim_job() ◀───┤ 每 2s 轮询        │
  │                    │                      │──────────────────▶│ status=running    │
  │                    │                      │◀─ parsing ────────┤ parse_pdf 按页     │
  │                    │                      │◀─ chunking ───────┤ chunk_blocks      │
  │                    │                      │◀─ embedding ──────┤ 批 8 条 ──────────▶│
  │                    │                      │                   │◀─ vectors ─────────┤
  │                    │                      │◀─ 删旧切片+写新切片(tsv 由 jieba 预分词)│
  │                    │                      │◀─ ready, chunk_count=n                │
  │  GET /documents    │                      │                   │                   │
  ├───────────────────▶│──────────────────────▶│                   │                   │
```

**关键设计点**

1. **去重在写盘之后、建记录之前**：sha256 是边写边算的，不读两遍文件。
2. **切片与向量在 worker 侧**：API 只负责收，避免大文件把 web 进程拖死。
3. **状态机单调向前**：`uploaded→parsing→chunking→embedding→ready|failed`，失败不回退。
4. **幂等**：重跑先 `DELETE FROM chunks WHERE doc_id=...` 再写，`UNIQUE(doc_id,seq)` 兜底。
5. **向量失败策略由 `EMBED_REQUIRED` 决定**：true → 整篇 `failed`（不写不可检索的数据）；
   false → 落 `embedding=NULL`、仅关键词可检索（**仅供联调**，此时闸门失效）。

### 4.2 问答

```
客户端                     api                        postgres              LLM
  │ POST /api/query         │                            │                    │
  ├────────────────────────▶│ 取 user(dept)               │                    │
  │                         ├─ jieba 分词 ─┐               │                    │
  │                         ├─ embed(问题) ─┴─▶ 向量        │                    │
  │                         ├─ HYBRID SQL（含 ACL）────────▶│                    │
  │                         │◀─ ≤40 条候选 + rrf + cosine ─┤                    │
  │                         ├─ rerank(问题, 候选文本) ─────────────────────────▶│(embed 服务)
  │                         │◀─ (idx, score)[] ──────────────────────────────────┤
  │                         ├─ should_refuse?               │                    │
  │                         │   是 → 直接吐拒答，不调 LLM     │                    │
  │  event: retrieval       │◀ 先发检索统计（count/top_score）                    │
  │◀────────────────────────┤                            │                    │
  │  event: token × N       ├─ stream_chat(上下文+问题) ───────────────────────▶│
  │◀────────────────────────┤◀─ delta ────────────────────────────────────────────┤
  │  event: citations       │◀ 结构化引用（标题/页码/片段/score）                  │
  │  event: done            │◀ refused:false                                     │
```

**为什么闸门在生成之前**：如果先把上下文丢给模型再让它"判断有没有"，
模型倾向于"努力回答"，拒答就变成概率事件。闸门是确定性代码，不通过就不调用模型，
既省钱也不会编。

### 4.3 失败与重试

| 失败点 | 行为 | 是否自动重试 |
|---|---|---|
| 解析失败（加密/扫描件） | `failed` + `error_code=parse_empty` | 否（重试也没用） |
| 向量服务 5xx/超时 | `EMBED_REQUIRED=true` → `failed` | 否；修好服务后重传 |
| 重排失败 | 降级为 RRF 排序，日志 warning | 是（下次请求自然重试） |
| LLM 超时/欠费 | SSE `event: error`，已吐出的 token 保留 | 否（用户重问） |
| DB 连接断 | 请求 500；连接池自动重连 | 是（下一次请求） |
| worker 崩溃 | 作业停留 `running` | **否（已知缺口：无超时回收）** |

## 五、数据设计

### 5.1 表职责

| 表 | 职责 | 关键约束 |
|---|---|---|
| `departments` | 组织树 | `name UNIQUE`、`parent_id` 自引用 |
| `users` | 账号与归属 | `api_token UNIQUE`、`role ∈ {member,editor,admin}` |
| `documents` | 文档主记录与状态 | `UNIQUE(dept_id, sha256)` 去重 |
| `chunks` | 切片 + 向量 + tsv | `UNIQUE(doc_id, seq)`、`vector(1024)` |
| `acl` | 显式授权 | 主键 `(doc_id, subject_type, subject_id)` |
| `jobs` | 入库队列 | 局部索引 `WHERE status='queued'` |
| `audit_logs` | 审计（**当前未写入**） | — |
| `schema_migrations` | 迁移记录 | 文件名主键 |

### 5.2 文档状态机

```
uploaded ──▶ parsing ──▶ chunking ──▶ embedding ──▶ ready
    │           │            │            │
    └───────────┴────────────┴────────────┴──────▶ failed (error_code, error_msg)
```

- 只有 `ready` 参与检索（所有检索 SQL 都带 `d.status='ready'`）。
- `failed` 必须带 `error_code`，否则前端无法解释"为什么没进去"。

### 5.3 索引策略

| 索引 | 类型 | 参数 | 理由 |
|---|---|---|---|
| `idx_chunks_hnsw` | HNSW | `m=16, ef_construction=64` | 单机十万级切片够用；建表后建，空表建反而慢 |
| `idx_chunks_tsv` | GIN | 默认 | 关键词路召回 |
| `idx_chunks_dept` | B-tree | — | 权限过滤辅助 |
| `idx_jobs_claim` | 局部 B-tree | `WHERE status='queued'` | 队列扫描只碰待处理行 |

**维度锁死**：`vector(1024)` 写死在 DDL。换模型必须改 DDL + 全量重跑，
不允许"同时兼容两种维度"——那会让距离计算悄悄错位。

## 六、接口设计

### 6.1 端点清单

| 方法 | 路径 | 用途 | 鉴权 |
|---|---|---|---|
| GET | `/` | 单页验收台 | 否 |
| GET | `/api/health` | 健康与配置状态 | 否 |
| GET | `/api/me` | 当前用户/部门/角色 | 是 |
| GET | `/api/documents` | 可见文档列表 | 是 |
| GET | `/api/documents/{id}` | 文档详情（含状态、错误） | 是 |
| POST | `/api/ingest/file` | 上传文件 | 是 |
| POST | `/api/ingest/text` | 文本入库 | 是 |
| POST | `/api/search` | 只检索不生成（评测用） | 是 |
| POST | `/api/query` | SSE 问答 | 是 |

详细参数与错误码见 [04-API接口文档](04-API接口文档.md)。

### 6.2 约定

1. **错误一律 JSON**：`{"detail": "..."}`，HTTP 状态码承载语义。
2. **SSE 事件固定四类**：`retrieval` / `token` / `citations` / `done`，异常走 `error`。
3. **`/api/search` 与 `/api/query` 共用检索路径**：保证评测分数就是线上分数。
4. **分页暂不做**：文档量级在千级以内，`LIMIT` 足够；超过再补 cursor。

## 七、架构决策记录（ADR）

### ADR-01 不用 ORM，手写 SQL

- **背景**：权限谓词必须出现在每一条检索 SQL 里。
- **选择**：psycopg3 + 具名参数 + 集中 SQL 常量。
- **理由**：ORM 的 `filter()` 很容易被后人绕过；手写 SQL 一眼能看出有没有 ACL。
- **代价**：CRUD 样板代码变多；复杂关联要自己拼。
- **替代方案**：SQLAlchemy 2.0（被否：多一层抽象，权限更难审）。

### ADR-02 向量与全文同库（PostgreSQL）

- **背景**：需要向量检索 + 中文关键词检索 + 事务一致性。
- **选择**：pgvector 0.8.7 + tsvector，单库双索引。
- **理由**：省掉 Milvus/ES 两个中间件；切片与文档状态天然同事务。
- **代价**：千万级向量后性能不如专用库；HNSW 参数需手工调。
- **触发换库的条件**：切片 > 500 万，或 P95 检索 > 1 s。

### ADR-03 队列用表，不用 Redis/Celery

- **背景**：入库是异步任务，量级低（日均几十篇）。
- **选择**：`jobs` 表 + `FOR UPDATE SKIP LOCKED` + 单 worker 轮询 2 s。
- **理由**：少一个组件就少一类故障；任务状态天然可查、可审计。
- **代价**：轮询有最多 2 s 延迟；没有定时/重试策略（当前不重试）。
- **替代方案**：Celery + Redis（被否：为一个低频队列引入两个组件不划算）。

### ADR-04 PDF 解析用 pypdfium2

- **背景**：需要页级定位，且要商用。
- **选择**：pypdfium2 按页抽取文本。
- **理由**：许可证宽松（BSD/Apache），无 AGPL 传染；页级 API 直接。
- **代价**：复杂排版（双栏、表格）抽取质量一般；无 OCR。
- **替代方案**：PyMuPDF（被否：AGPL）、pdfplumber（表格好但慢、依赖重）。

### ADR-05 中文检索：jieba 预分词 + tsvector

- **背景**：PG 的 `simple` 配置不切中文，`zhparser` 需要编译扩展。
- **选择**：入库与查询都先 jieba 切词、空格连接，再交给 `simple` 配置。
- **理由**：不引入 PG 扩展；分词规则在应用层可改、可加词典。
- **代价**：**入库与查询必须用同一套分词**，改一边就检索归零且不报错。
- **纪律**：两处都走 `search/tokenize.py`，禁止各写一份。

### ADR-06 向量化本地化（fastembed + onnxruntime）

- **背景**：云端 embedding 余额耗尽即停摆，且按量计费不可控。
- **选择**：独立 `embed` 容器，加载 jina-embeddings-v3（1024 维），暴露 OpenAI 兼容接口。
- **理由**：零边际成本、数据不出网；维度与原 DDL 一致，无需迁移存量。
- **代价**：常驻 5.66 GB 内存、3.2 GB 磁盘；首次启动需下载权重。
- **替代方案**：bge-m3（fastembed 0.7.x 不支持）、云端 API（保留为配置项）。

### ADR-07 SSE 而非 WebSocket

- **背景**：只需服务端单向推送 token。
- **选择**：`text/event-stream` + `X-Accel-Buffering: no`。
- **理由**：HTTP 原生、curl 可测、无连接管理。
- **代价**：不能中途取消生成（客户端断开即放弃，服务端不感知）。

### ADR-08 权限在 SQL 谓词，不在应用层

- **背景**：检索是 `LIMIT 40` 的候选截断，先查后过滤会"把别人的 40 条取回来"。
- **选择**：`ACL` 常量拼进 `WHERE`，四条通路（本人/本部门/显式 ACL/company）。
- **理由**：过滤发生在候选生成之前，物理上不可能越权。
- **代价**：`dept` 语义被写死为"等于"，多级组织需改 SQL。
- **纪律**：`sql.py` 是全系统唯一一处 ACL，代码评审重点盯这里。

## 八、降级与容错矩阵

| 故障 | 用户看到什么 | 系统行为 | 数据影响 |
|---|---|---|---|
| embed 容器挂 | 新文档 `failed`；问答仍可走关键词 | `embed_required=true` 拒写入 | 不产生脏数据 |
| 重排模型加载失败 | 答案质量下降，无报错 | 501 → 退回 RRF 排序 | 无 |
| LLM 欠费 | `event: error: 生成失败` | 已吐 token 保留 | 无 |
| postgres 挂 | 全站 500（`/` 仍可打开） | 连接池重连 | 事务回滚 |
| worker 挂 | 文档停在 `parsing/embedding` | 重启后继续抢队列 | **running 作业可能卡死** |
| 磁盘满 | 上传 500，入库失败 | 无自动清理 | 需人工清理 |

**没有做的容错（明说）**：worker 作业超时回收、上传断点续传、LLM 重试退避。
这三项都属于"量上来之后再做"，现在做是过度设计。

## 九、安全设计

| 面 | 措施 | 残余风险 |
|---|---|---|
| 身份 | Bearer Token（随机 32 字节），DB 明文存 | 无过期、无轮换、泄露即长期有效 |
| 授权 | SQL 谓词四通路，候选截断前过滤 | 多级部门未支持；`company` 全公司可见需谨慎使用 |
| 传输 | 内网 HTTP（未上 TLS） | 同网段可嗅探，建议前置 nginx + 证书 |
| 文件 | 扩展名白名单 + 大小限制 + 服务端生成路径 | 无病毒扫描 |
| 路径穿越 | `storage` 用 doc_id 生成路径，不拼用户文件名 | — |
| 密钥 | `.env` 600 权限、不入库、`.gitignore` | 备份脚本需排除 |
| 出网 | 只有 LLM 请求出网；embed 绑 `127.0.0.1:8090` | 未抓包验证（NFR-07） |
| 提示注入 | 资料片段来自内部文档，风险低 | 恶意文档可诱导模型，但闸门与引用仍在 |

**最重要的一条**：`company` 可见性等于全公司公开。上传界面必须写清楚，
否则一份标了"内部"的制度会被全公司搜到。

## 十、部署设计

| 项 | 设计 | 理由 |
|---|---|---|
| 编排 | 单机 `docker compose`，四服务 | 无 K8s，降低运维门槛 |
| 端口 | 宿主 `9527` → 容器 `8088` | 甲方指定，避开冲突 |
| embed 暴露 | `127.0.0.1:8090` 仅回环 | 模型服务不对外，防滥用 |
| 重启策略 | `restart: unless-stopped` | 崩溃自愈；需 Docker 开机自启配合 |
| 依赖顺序 | `depends_on` + `healthcheck`（pg_isready / embed /health） | 避免 api 抢跑 |
| 数据持久化 | 命名卷 `pgdata` / `filedata` / `models` | 容器删了数据还在 |
| 镜像 | slim + `LANG=C.UTF-8` + `PYTHONUTF8=1` | 避免中文路径与非 UTF-8 读取 |
| 首次启动 | 下载 3.2 GB 权重 | 文档必须提前告知，否则以为卡死 |

## 十一、扩展点（P1 怎么接）

| 能力 | 接入点 | 改动面 |
|---|---|---|
| OCR | 新增 `parsers/pdf_ocr.py`，registry 按"抽取为空"分流 | 一个文件 + 依赖 |
| Word/Excel | 新增 parser，`registry` 加扩展名 | 一个文件 |
| 视频 | `source_type='video'`，locator 改 `{start,end}`（`format_locator` 已支持） | parser + 转码任务 |
| 文档删除 | 新增 `DELETE /api/documents/{id}`，级联删 chunks + 文件 | 一个端点 |
| SSO | `deps.py` 换 token 解析，`users` 加外部 id | 一个文件 |
| 多轮 | 请求带 `history`，`answer.py` 拼消息 | 一个函数，但要加会话存储 |

**扩展的前提**：`locator` 不为空、权限谓词不绕过、切片可重跑。
这三条守住，接什么格式都不会伤到主链路。

## 十二、技术债务（带还债条件）

| 债务 | 影响 | 何时必须还 |
|---|---|---|
| `audit_logs` 表存在但未写入 | 无法追溯"谁问过什么、谁传了什么" | 合规要求出现时 |
| worker 无超时回收 | 崩溃后作业卡 `running` | 出现第一次卡死 |
| 无迁移回滚脚本 | 只能向前迁移 | 生产库第一次改 schema |
| 无 TLS | 内网明文 | 跨网段访问前 |
| 单 worker | 批量入库排队 | 单日入库 > 200 篇 |
| 阈值未重标定 | 误拒/漏拒 | **接入真实文档后立刻**（最高优先） |
| 无前端框架 | 验收台功能有限 | P1 产品化 |
