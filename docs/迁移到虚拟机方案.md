# 迁移到虚拟机开发 · 方案

> 场景：本机磁盘吃紧（460GB 用了 378GB，剩 50GB / 89%），想把本项目的开发环境搬到虚拟机。
> 记录时间：2026-10-30

---

## 零、先算一笔账：这个项目不是占空间的那个

| 对象 | 实际占用 | 说明 |
|---|---|---|
| 本仓库代码 | **116 KB** | `server/` 全部源码 |
| 本仓库 git 历史 | 320 KB | 两个 commit |
| 本仓库总计 | 129 MB | 其中 **128 MB 是 `.venv`**（可随时重建，不必迁） |
| 迁移包（实测） | **112 KB** | `dist/kb-deskpet-migrate-20261030-1700.tgz` |
| Docker 整体 | **21 GB** | `~/Library/Containers/com.docker.docker` |
| ├ 镜像 | 19.0 GB | 其中 6.6 GB 可回收 |
| ├ 构建缓存 | 1.63 GB | 全部可回收 |
| └ 数据卷 | 539 MB | 其中 490 MB 未使用 |

**结论**：把知识库项目搬到虚拟机，本机只能省下 ~130MB（而且删掉 `.venv` 就能省 128MB）。
真正吃空间的是 **Docker 里的 21GB**，其中大头是 Dify 全栈（`dify-api` 3.94GB、`plugin-daemon` 2.21GB、`agent-backend` 1.52GB 等）和两个旧项目的镜像（`huobao-drama` 系列 4.8GB、`mysql`/`mariadb` 1.6GB）。

所以"迁移"这件事要先分清目的：

| 你的目的 | 该做什么 | 迁本项目有用吗 |
|---|---|---|
| **只是想让本机多出空间** | 清 Docker（见第五章），能立刻回收 8–17GB | ❌ 基本无用 |
| **想换一台机器长期开发** | 迁到远程/云端 Linux 虚拟机 | ✅ 有用，且顺带把 Docker 也挪走 |
| **想隔离环境、避免互相干扰** | 迁到虚拟机 | ✅ 有用 |

## 一、先明确一个反直觉的点：本机装虚拟机不省空间

实测本机 **没有安装任何虚拟机软件**（Parallels / VMware / UTM / VirtualBox 都不存在），所以"本机 VM"这条路要先付出：

| 开销 | 大小 |
|---|---|
| 虚拟机软件 | Parallels ~500MB，UTM 免费 ~200MB |
| Ubuntu 24.04 ARM64 镜像 | ~2.5GB（iso）+ 安装后 8–12GB |
| 虚拟机磁盘（开发够用） | 最少 40GB，建议 60GB |
| Docker Desktop 在 VM 里再装一套 | +2GB 镜像 |

**净效果：为了省 50GB，先花掉 60GB。** 除非把虚拟机磁盘文件放到外置 SSD，否则这条路会让本机更紧张。

所以下面只推荐两条路：**A 云端/远程 Linux 虚拟机**（真释放）和 **B 本机只瘦身不迁移**（最快见效）。

## 二、路线对比

| | A. 远程 Linux VM（推荐） | B. 本机瘦身（不迁移） | C. 本机 VM + 外置盘 |
|---|---|---|---|
| 本机释放空间 | 20 GB+（Docker 可全清） | 8–17 GB | 0（VM 盘在外置盘） |
| 需要额外成本 | 云主机 4C8G 约 ¥100–200/月 | 0 | 外置 SSD + 软件 |
| 迁移耗时 | 半小时 | 十分钟 | 半天（先装环境） |
| 适合长期开发 | ✅ | ❌ 空间还会再满 | ✅ |
| 断网可用 | ❌ | ✅ | ✅ |

**建议**：先做 B（十分钟，立刻见效，见第五章），同时开 A（云主机 4C8G / 60–100GB，装 Ubuntu 24.04）。B 做完你会发现可能根本不用迁。

## 三、路线 A：迁移步骤（已脚本化，两条命令）

### 3.1 目标机规格

| 项 | 最低 | 建议 | 理由 |
|---|---|---|---|
| CPU | 2 vCPU | 4 vCPU | 向量化是网络 IO，但 PG + Docker 编译要 CPU |
| 内存 | 4 GB | 8 GB | postgres 给了 `shm_size: 1gb`，加 api/worker/构建 |
| 磁盘 | 40 GB | 60–100 GB | 镜像 ~2GB，后期文档与向量增长快 |
| 系统 | Ubuntu 22.04 / 24.04 LTS | 同左 | 脚本按 apt + get.docker.com 写 |
| 架构 | x86_64 或 ARM64 均可 | 同左 | 全部是官方多架构镜像 |
| 网络 | 能访问 docker hub、api.siliconflow.cn、apihub.agnes-ai.com | | 三个外部依赖 |

### 3.2 源机：打包（一条命令）

```bash
cd ~/kb-deskpet
bash deploy/pack.sh
```

产物：`dist/kb-deskpet-migrate-<时间戳>.tgz`，**实测 112 KB**。包里是：

| 内容 | 为什么带 |
|---|---|
| 完整仓库（含 `.git`） | 到目标机仍是正常 git 仓库，历史不丢 |
| `env.production`（即 `.env`） | key 不用手抄；权限 600 |
| `kb.dump`（可选） | 仅当库里有真实文档时才生成；当前库里 0 篇，自动跳过 |

不带：`.venv`（重建 30 秒）、`server/data`（上传的原始文件，需要单独 rsync）、`dist`。

### 3.3 传输

```bash
scp dist/kb-deskpet-migrate-*.tgz <用户>@<VM_IP>:~/
```

`.env` 里有 API key，**走 scp，不要发微信/邮件**。若走公网，建议先 `scp` 到跳板再转，或临时用 `age`/`gpg` 加密。

### 3.4 目标机：一条命令起服务

```bash
bash bootstrap.sh kb-deskpet-migrate-<时间戳>.tgz
```

脚本做六件事：装 Docker → 解包到 `~/kb-deskpet` → 写 `.env` → `docker compose up -d --build` → 等 PG 就绪 → 有 dump 就 `pg_restore`、没有就 `migrate.py` → 跑 `check_keys.py` 自检。

脚本幂等：重复执行只更新代码并重启容器，数据在 docker volume 里不受影响。

### 3.5 迁移后校验清单（缺一条不算完成）

| 检查 | 命令 | 期望 |
|---|---|---|
| 容器状态 | `docker compose ps` | postgres/api/worker 三个 Up，postgres healthy |
| 表结构 | `docker compose exec api python scripts/migrate.py` | 输出 `migrate done`，无报错 |
| 三个 key | `docker compose exec api python scripts/check_keys.py` | 数据库/embedding/生成 三项 ✅ |
| 建账号 | `docker compose exec api python scripts/seed.py` | 打印 token |
| 端到端 | 打开 `http://<IP>:8088`，拖一份 PDF 提问 | 2 分钟内出答案，带页码引用 |
| 重启存活 | `sudo reboot` 后 `docker compose ps` | 三个容器自动回来 |

### 3.6 回滚

代码在源机没动过，数据库是新建的空库，**回滚成本为零**：目标机 `docker compose down` 即可，源机继续用。

## 四、Dify 那条线怎么办

Dify 全栈 15 个容器，占 Docker 21GB 里的大部分（镜像约 11GB + 卷）。它目前的状态是"部署完成、使用 0"（1 个 app、0 个知识库），和知识库项目是**两条独立的线**。

三个选择：

| 方案 | 做法 | 释放 | 代价 |
|---|---|---|---|
| **① 停用不删**（建议） | `cd dify/docker && docker compose down` | 容器内存 3.3GB 立刻释放，磁盘不变 | 下次 `up -d` 就能回来，数据全在 |
| **② 迁到同一台 VM** | 打包 `dify/docker` + `volumes/`（约 7–8GB）后 scp | 本机 ~19GB | 传输慢（家用上行 1–2 小时） |
| **③ 彻底删除** | `docker compose down -v` + `docker rmi` 相关镜像 | 本机 ~19GB | 配置与历史会话全丢，需重装重配 |

推荐 ①：先 `down`，观察一周确定不用了再考虑 ③。**注意 Dify 的 `restart: always` 只在 Docker 启动时生效，`down` 之后不会自己回来**，这正是你要的效果。

## 五、路线 B：本机瘦身清单（只建议，未执行任何删除）

按"回收量 / 风险"排序：

| # | 动作 | 命令 | 回收 | 风险 |
|---|---|---|---|---|
| 1 | 清构建缓存 | `docker builder prune -f` | **1.63 GB** | 无（下次构建重新生成） |
| 2 | 清旧项目镜像 | `docker rmi action-short-drama-video-generator-huobao-drama:latest huobao/huobao-drama:latest huobao-frontend-build:latest mysql:8.4 mariadb:11` | **6.45 GB** | 低（这三个镜像当前没有容器在用；旧项目要跑时需要重新 build） |
| 3 | 清悬空镜像与未用卷 | `docker image prune -f && docker volume prune -f` | **0.5–1 GB** | 低（只删无标签镜像和未挂载卷） |
| 4 | 停 Dify | `cd ~/WorkBuddy/本地部署dify/dify/docker && docker compose down` | 内存 3.3GB | 无（数据全在，随时 up） |

## 六、迁移后开发体验的三个变化

1. **没有 Docker Desktop 的 GUI**：`docker compose logs -f` 变成主要观察手段，`make logs` 已经封好。
2. **代码编辑要重新选通道**：两个选项——① VS Code Remote-SSH 直接编辑 VM 上的代码（推荐，改完即时生效）；② 本机编辑 + `rsync -a --delete --exclude=.venv ~/kb-deskpet/ vm:~/kb-deskpet/` 同步。**不要用 git push/pull 当同步手段**，每次都要 commit，很快就会乱。
3. **端口与安全**：8088 对公网开放前必须挂 Nginx + HTTPS，`ACL` 那套只在 SQL 里，传输层没加密等于白做。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `.env` 泄漏 | API key 被盗刷 | scp 传输、权限 600、不 commit（`.gitignore` 已含） |
| VM 磁盘写满 | postgres 崩溃、写入失败 | 装 `node_exporter` 或最简单的 `df -h` 定时告警；不要给 PG 开自动扩容快照 |
| 云主机 IP 变化 | 前端地址失效 | 用域名 + A 记录，别把 IP 写死在前端 |
| 忘了配开机自启 | 重启后服务全灭（Dify 已经踩过一次） | `docker compose` 已设 `restart` 默认行为；**迁移后务必做 3.5 的重启存活测试** |
| 在家/公司网络不同 | 连不上 VM | 优先选固定公网 IP；或内网穿透 |

### 9.3 迁移过程中发现并修掉的三个真问题

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 容器内报 `no migration found in /migrations` | `migrate.py` 用 `parents[2]` 算迁移目录，容器里是 `/app/scripts/` → 得到 `/migrations` | 改为按候选顺序探测：`MIGRATIONS_DIR` → `/app/migrations` → `<repo>/migrations` |
| 2 | 迁移报 `UnicodeDecodeError: 0xa3 at position 45` | macOS `tar` 给带扩展属性的文件生成了 `._0001_init.sql` 影子文件（AppleDouble），被当成真的 `.sql` 排序读入 | 打包时 `export COPYFILE_DISABLE=1` + `--exclude='._*'`；`migrate.py` 跳过 `._` 前缀；bootstrap 解包后清理 |
| 3 | `read_text()` 在 slim 镜像里默认编码不是 UTF-8 | `LANG` 未设置，`locale.getpreferredencoding()` 退化 | `read_text(encoding="utf-8")` + Dockerfile 设 `LANG=C.UTF-8`、`PYTHONUTF8=1` |

附带修掉：`bootstrap.sh` 里 `docker compose exec -T` 会吃掉 stdin（脚本本身从 stdin 读），统一加 `</dev/null`；改用「先把脚本 scp 成文件再执行」彻底绕开。

### 10.1 端口 8088 → 9527

| `deploy/bootstrap.sh` | 结束提示改成从 `.env` 读 `APP_PORT`，不再硬编码 |
| `Makefile` | `make up` 的提示用 `$${APP_PORT}` |

### 10.2 三个 key 的真实能力（实测）

| 能力 | 供应商 | 结果 |
|---|---|---|
| 生成 | Agnes `agnes-3.0-flash` | ✅ 200，流式正常 |
| 向量化 | Agnes | ❌ `/v1/embeddings` 返回 `model_not_found`；该账号总共只有 6 个模型，无任何 embedding |
| 向量化 | 硅基流动 `BAAI/bge-m3` | ❌ **402 余额不足**（`code 30001`） |
| 重排 | 硅基流动 `BAAI/bge-reranker-v2-m3` | ❌ 同上 402 |

结论：**embedding 与 rerank 都卡在硅基流动账户余额为 0**，换模型名无用
（bge-m3 / Qwen3-Embedding-0.6B / bge-large-zh 全部 402）。充值后即通，
`bge-m3` 单价极低，¥10 约等于一两千万 token，够本部门用很久。

### 10.3 新增 `EMBED_REQUIRED` 开关

向量化不可用时有两种合理策略，做成显式开关而不是隐式兜底：

| 值 | 行为 | 适用 |
|---|---|---|
| `true`（默认） | 整篇文档置 `failed`，`error_msg` 写明原因 | 生产，宁可失败也不留不可检索的数据 |
| `false` | 落 `embedding=NULL`、`embed_model='none'`，`ext.embed_degraded=true`，仅关键词可检索 | 联调 / 余额欠费期间保可用 |

打开后整条链路仍可用：关键词检索（jieba + tsvector）→ Agnes 生成 → 带页码引用。
已知局限：此模式下 `should_refuse` 拿不到 rerank/cosine 分数，**拒答闸门实际关闭**，
只有「一条都没召回」才会拒答。恢复向量与重排后闸门才完整生效。

### 10.4 两个真 bug（均已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `psycopg.errors.InvalidTextRepresentation: invalid input syntax for type uuid: "None"`，worker 每 2 秒崩一次、日志刷屏 | `claim_job()` 返回复合类型 `jobs`，**队列为空时 `SELECT * FROM claim_job()` 仍返回「一行全 NULL」**，`if not job` 判不出来，于是把 `doc_id='None'` 当真任务 | 迁移 `0002` 改为 `RETURNS SETOF jobs`（空队列 0 行）；`worker.py` 再加 `job["id"] is None` 兜底 |
| 2 | 上一条迁移首次执行报 `cannot change return type of existing function` | PostgreSQL 不允许 `CREATE OR REPLACE` 改返回类型 | 0002 里先 `DROP FUNCTION IF EXISTS claim_job()` 再重建 |

### 10.6 一个操作教训

`rsync` 时若把 `.` 整个目录传过去，会**覆盖目标机的 `.env`**（key 与端口全部丢失，

显式排除 `.env`，以后同步只用它。

## 十一、C 方案落地：本地 embedding + 本地重排（2026-10-31 完成）

### 11.1 为什么放弃云端

| 方案 | 结论 |
|---|---|
| 硅基流动 `bge-m3` | key 有效但**余额 0**，embeddings/rerank 全部 `402 / code 30001`，换模型名无用 |
| Agnes | 账号只有 6 个模型（chat ×3、image ×3），**无任何 embedding 模型**，`/v1/embeddings` → `model_not_found` |
| OpenRouter 免费 embedding | 维度非 1024（需改 DDL），且免费额度不稳定，不适合做入库基线 |

因此改在本机跑：**一次性下载，永久免费，无调用次数限制**。

### 11.2 选型的一处修正

原计划用 `BAAI/bge-m3`，但 **fastembed 0.7.4 已不再内置该模型**（实测 `list_supported_models()` 无此项，
`TextEmbedding("BAAI/bge-m3")` 直接抛错）。改为同维度可用的：

| 角色 | 模型 | 维度 | 体积 |
|---|---|---|---|
| 向量化 | `jinaai/jina-embeddings-v3` | **1024** ✅ | ~2.3 GB |
| 重排 | `jinaai/jina-reranker-v2-base-multilingual` | — | ~0.9 GB |

维度仍是 1024，**DDL 与已有 `vector(1024)` 列不用改**。以后若换成 bge-m3（如自建
text-embeddings-inference），只要维度相同，旧向量仍可复用。

### 11.3 实现

新增 `server/embed_service/app.py`（约 200 行），对外暴露 **OpenAI 兼容**接口：

| 端点 | 说明 |
|---|---|
| `POST /v1/embeddings` | 返回 `data[].embedding`，维度从模型实测得到并回报 |
| `POST /v1/rerank` | 返回 `results[].relevance_score`，与硅基流动同格式 |
| `GET /health` | `{status, dim, embed_ready, rerank_ready, *_error}` |
| `GET /v1/models` | 回报**实际加载**的模型名 |

三个设计要点：
1. **后台线程加载模型**，容器立即 healthy，`/health` 如实报 `loading/ok/error`，不会因为下载慢被判死。
2. **端口仍用 8088**（容器内），宿主映射到 **127.0.0.1:8090**（只本机可达，不对外暴露）。
3. **`HF_HUB_DISABLE_XET=1`** —— 通过 hf-mirror 下载时 xet/CAS 协议会返回 401，关掉后走普通 HTTP 正常。

`docker-compose.yml` 新增 `embed` 服务（含 `models` 命名卷、`start_period: 300s` 的宽容健康检查、
`restart: unless-stopped`）。应用侧只改 `.env`，代码零改动：

```ini
EMBED_BASE=http://embed:8088/v1
EMBED_MODEL=jinaai/jina-embeddings-v3
EMBED_API_KEY=local
EMBED_DIM=1024
EMBED_REQUIRED=true          # 本地服务可靠，回到严格模式
RERANK_BASE=http://embed:8088/v1
RERANK_MODEL=jinaai/jina-reranker-v2-base-multilingual
RERANK_API_KEY=local
```

### 11.4 实测数据

| 项 | 结果 |
|---|---|
| 冷启动（已是本地权重） | **约 6 秒**就绪（首次含下载则需数分钟） |
| 向量质量 | 相关句 cosine **0.571**，无关句 **0.030** |
| 单条向量延迟 | ~1.5 s（含 HTTP；批量 8 条约 2 s，摊薄后 ~0.25 s/条） |
| 内存占用 | embed 容器 **5.66 GB**（两个模型常驻），全机已用 6/15 GB |
| 模型卷 | 3.2 GB |
| 稳定性 | 连续运行 **14 小时**无重启，healthy |

> 注：曾实验并发加载多个 `TextEmbedding` 实例做参数对比，被 OOM 杀掉——这是**实验方式的问题**，
> 不是服务缺陷。服务本身单实例常驻，稳定。

### 11.5 端到端复测（真实向量 + 真实重排）

重新入库同一份 PDF 后：

```
问：住宿费的报销标准是多少？
retrieval  {"count": 1, "top_score": 0.7574}      ← 降级模式时是 0.0164
citations  [{"locator_text":"第 1 页","title":"差旅与休假制度","score":0.7574}]
answer     住宿费报销标准为每晚上限五百元，超标部分自理 [1]。
done       {"refused": false}
```

**拒答闸门恢复生效**（这是 C 方案最重要的收益，降级模式下它是关闭的）：

```
问：公司的股权激励计划怎么申报？
retrieval  {"count": 1, "top_score": 0.1752}      ← 低于阈值 0.35
done       {"refused": true}
answer     知识库里没有查到相关内容。可以换个说法再问，或者把这部分资料先传上来。
```

注意 `count` 为 1 但 `top_score` 只有 0.1752，说明**向量召回的“最近邻”不代表相关**——
这正是必须有分数闸门、不能只靠“有没有召回”判断的原因。

```
                           │              │
                   ┌───────▼──────┐  ┌────▼─────────────┐
                   │ postgres     │  │ embed :8088      │
                   │ pgvector+tsv │  │ jina-v3 (1024d)  │
                   │              │  │ jina-reranker-v2 │
                   └──────────────┘  └──────────────────┘
                           │

```

四个容器，只有生成走外网；向量化、重排、存储全部本地。
