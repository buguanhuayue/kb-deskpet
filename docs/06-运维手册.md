# 06 · 运维手册

> 面向：运维。目标是"出问题时能自己定位并恢复"，不依赖开发者。

## 一、系统构成回顾

| 容器 | 作用 | 挂了会怎样 | 内存 |
|---|---|---|---|
| `postgres` | 数据 + 向量 + 全文索引 | **全站不可用** | ~40 MB |
| `embed` | 本地向量化 + 重排 | 入库全部失败；查询降级为纯关键词 | **~5.7 GB** |
| `api` | HTTP 接口 | 页面打不开 | ~100 MB |
| `worker` | 异步入库 | 文档永远停在 `uploaded` | ~90 MB |

四个都是 `restart: unless-stopped`，崩了会自动拉起。**但 Docker 守护进程本身要开机自启**（见下）。

## 二、日常巡检

### 每日（1 分钟）

```bash
cd ~/kb-deskpet
# 一条命令看全貌
docker compose ps
curl -s http://127.0.0.1:9527/api/health
```

期望：四个 Up（postgres/embed 为 healthy），health 里 `db:ok` +
`embed/rerank/llm` 均为 `configured`。

### 每周（5 分钟）

```bash
# 1. 失败文档
docker compose exec -T postgres psql -U kb -d kb -c \
  "SELECT title, status, error_code, left(error_msg,60) FROM documents
   WHERE status='failed' ORDER BY created_at DESC LIMIT 10;" </dev/null

# 2. 卡住的任务（attempts 一直涨但不 done）
docker compose exec -T postgres psql -U kb -d kb -c \
  "SELECT id, doc_id, status, attempts FROM jobs
   WHERE status IN ('queued','running') ORDER BY created_at LIMIT 10;" </dev/null

# 3. 向量覆盖是否完整（有切片但没向量的说明降级过）
docker compose exec -T postgres psql -U kb -d kb -c \
  "SELECT count(*) total, count(embedding) with_vec FROM chunks;" </dev/null

# 4. 磁盘与内存
df -h / ; free -g | head -2
docker system df

# 5. 容器有没有反复重启（RESTART 次数不为 0 要查）
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

### 每月

- 做一次**恢复演练**（不只是备份，要验能恢复）
- 检查 `.env` 里 key 是否临近过期
- 看日志里有无持续出现的 warning

## 三、备份与恢复

### 3.1 备份

两样东西必须一起备：**数据库** + **原始文件**。

```bash
cd ~/kb-deskpet
STAMP=$(date +%Y%m%d-%H%M)

# 1. 数据库（含结构、切片、向量）
docker compose exec -T postgres pg_dump -U kb -d kb -Fc > ~/backup-$STAMP.dump </dev/null

# 2. 原始文件（filedata 命名卷）
docker run --rm -v kb-deskpet_filedata:/data -v ~:/out alpine \
  tar czf /out/files-$STAMP.tgz -C /data .

# 3. 配置（含密钥，单独保管，不要和上面两个放一起）
cp .env ~/backup-env-$STAMP.txt && chmod 600 ~/backup-env-$STAMP.txt

ls -lh ~/backup-$STAMP.dump ~/files-$STAMP.tgz
```

> 卷名可能因项目目录名不同而变化，用 `docker volume ls | grep filedata` 确认。

**备份策略建议**：

| 频率 | 保留 | 存放 |
|---|---|---|
| 每日 | 7 天 | 本机 + 另一台机器 |
| 每周 | 4 周 | 异地或对象存储 |

`models` 卷**不需要备份**——3.2 GB 权重可重新下载。

### 3.2 恢复

```bash
cd ~/kb-deskpet

# 1. 停应用，保留数据库容器
docker compose stop api worker

# 2. 恢复数据库（--clean 会先删现有对象）
docker compose exec -T postgres pg_restore -U kb -d kb --clean --if-exists \
  < ~/backup-20261031-0900.dump

# 3. 恢复文件
docker run --rm -v kb-deskpet_filedata:/data -v ~:/in alpine \
  sh -c 'rm -rf /data/* && tar xzf /in/files-20261031-0900.tgz -C /data'

# 4. 起服务并验证
docker compose start api worker
docker compose exec -T api python scripts/check_keys.py </dev/null
```

### 3.3 恢复演练（每季度至少一次）

在**独立目录**跑一份恢复，不碰生产：

```bash
mkdir -p /tmp/restore-test && cd /tmp/restore-test
# 用不同端口起一套
PORT=9999 docker compose -f ~/kb-deskpet/docker-compose.yml up -d postgres
# 恢复 dump，查 count 是否与生产一致
```

演练要记三件事：耗时、是否一次成功、数据条数是否对得上。

## 四、日志

```bash
docker compose logs api --tail 100          # 接口层
docker compose logs worker --tail 100       # 入库流水线（最常看）
docker compose logs embed --tail 100        # 模型加载与推理
docker compose logs postgres --tail 100     # 数据库
docker compose logs -f --tail 50 api worker # 实时跟
```

### 各容器的关键日志行

| 容器 | 正常长这样 | 异常信号 |
|---|---|---|
| `api` | `api 启动 \| embed=... llm=...` | 启动后无该行 → 配置加载失败 |
| `worker` | `claim job=... doc=... attempt=1` 后接 `ready` | 每 2 秒重复同一行 → 队列空转 bug |
| `embed` | `embedding 就绪 ... dim=1024`、`rerank 就绪` | `加载失败` / 一直 `loading` |

**worker 日志量**：正常时几乎为空（空闲不打印）。如果日志疯涨，一定是循环出错，
先 `docker compose logs worker --tail 20` 看最后几行。

## 五、故障处置 Runbook

### 5.1 页面打不开

```bash
# ① 容器还在吗
docker compose ps
# ② 端口在听吗
ss -lntp | grep 9527
# ③ 应用自己怎么想
curl -s http://127.0.0.1:9527/api/health
# ④ 日志有没有异常
docker compose logs api --tail 40
```

| 定位 | 处置 |
|---|---|
| 容器没起 | `docker compose up -d`，看报错 |
| 端口没听 | 检查 `APP_PORT` 与端口占用 |
| `db: down` | 看 postgres 容器；`pg_isready` |
| 全正常但外部打不开 | 防火墙/安全组；`ufw status` |
| 全正常但某台机器打不开 | 该机器的代理设置（`no_proxy`） |

### 5.2 上传后一直 `uploaded`，不往下走

```bash
docker compose ps worker                       # worker 活着吗
docker compose logs worker --tail 30           # 有 claim 吗
docker compose exec -T postgres psql -U kb -d kb -c \
  "SELECT id,status,attempts,error FROM jobs ORDER BY created_at DESC LIMIT 5;" </dev/null
```

| 现象 | 根因 | 处置 |
|---|---|---|
| worker 不在 | 崩了或被 OOM | `docker compose up -d worker`，看 `dmesg | grep -i killed` |
| 有 job 但 status=queued，`run_after` 在未来 | 延迟重试 | 等到时间；或手工改 `run_after=now()` |
| job 一直 `running` 且 `locked_at` 很久 | worker 处理中崩了，任务没释放 | `UPDATE jobs SET status='queued', locked_at=NULL WHERE status='running' AND locked_at < now()-interval '10 min';` |
| job `failed` | 看 `error` 字段 | 修复根因后重置为 queued |

### 5.3 入库失败：`embed_failed` / 维度不匹配

```bash
docker compose exec -T embed curl -s http://127.0.0.1:8088/health
docker compose logs embed --tail 30
```

| 现象 | 处置 |
|---|---|
| `embed_ready: false` | 模型没加载成功，看 `embed_error`；确认 `HF_HUB_DISABLE_XET=1` |
| 一直 `loading` | 还在下载（首次 3.2 GB）；`docker run --rm -v kb-deskpet_models:/m alpine du -sh /m` 看进度 |
| 维度不是 1024 | 换错模型了，改 `EMBED_MODEL` 为 `jinaai/jina-embeddings-v3` |
| 容器 OOM 反复重启 | 内存不足，需 ≥ 8 GB；确认没有其他大内存进程 |

### 5.4 问答报错或答非所问

```bash
# 先看检索本身对不对（不调生成模型）
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"question":"<问题>"}' http://127.0.0.1:9527/api/search | python3 -m json.tool
```

| 检索结果 | 说明 | 下一步 |
|---|---|---|
| `count: 0` | 没有召回 | 文档没入库 / 没变 ready / 权限过滤掉了 |
| 有结果但 `rerank: null` | 重排服务挂了，已降级 | 修 embed 服务 |
| 有结果但 `rerank` 很低 | 确实不相关 → 拒答是正确的 | 补文档，不是 bug |
| `cosine` 高但 `rerank` 低 | 语义相近但实际无关 | **正常**，这正是要重排的原因 |

生成环节报错（返回 `event: error`）：

```bash
docker compose logs api --tail 20 | grep -i "生成失败"
# 通常是 LLM key 失效 / 余额 / 网络不通
curl -s -m 10 -o /dev/null -w "%{http_code}\n" $LLM_BASE/models -H "Authorization: Bearer $LLM_KEY"
```

### 5.5 机器重启后服务没起来

```bash
systemctl is-enabled docker     # 必须是 enabled
systemctl status docker
docker compose ps
```

若不是 `enabled`：`sudo systemctl enable docker`。这是**最常见的静默故障**，
服务挂了但没人知道，直到有人要用。

### 5.6 磁盘满

```bash
df -h /
docker system df
du -sh /var/lib/docker/volumes/*
```

```bash
docker system prune -f          # 清构建缓存与悬空镜像（安全）
docker image prune -a -f        # 删所有未使用镜像（谨慎）
```
**不要**动 `pgdata` / `filedata` / `models` 三个卷。

## 六、性能与容量

### 6.1 资源基线（实测）

| 项 | 数值 | 说明 |
|---|---|---|
| 内存总占用 | ~6 GB / 15 GB | embed 占 5.7 GB，是主要开销 |
| 冷启动（权重已下载） | ~6 秒 | 从 `restart` 到 `/health` 报 ok |
| 冷启动（首次下载） | 5–15 分钟 | 取决于带宽，3.2 GB |
| 单条向量 | ~1.5 s（含 HTTP） | 批量 8 条约 2 s，摊薄 0.25 s/条 |
| 单次问答（首字节） | 1–3 s | 含检索 + 重排 + 首 token |
| 单次问答（完整） | 3–8 s | 取决于答案长度与生成模型速度 |

### 6.2 容量估算

| 文档量 | 切片量（按每篇 20 片估） | 向量存储 | 建议 |
|---|---|---|---|
| 100 篇 | 2,000 | ~16 MB | 当前配置足够 |
| 1,000 篇 | 20,000 | ~160 MB | 当前配置足够 |
| 10,000 篇 | 200,000 | ~1.6 GB | 建议加 `ef_search` 调优，考虑独立 PG |
| 50,000+ 篇 | 1,000,000+ | ~8 GB | 需拆分 embed 到独立机器，PG 独立部署 |

向量存储粗算：1024 维 float32 ≈ 4 KB/条，加索引约 1.5 倍。

### 6.3 已知性能瓶颈

| 瓶颈 | 现状 | 可选优化 |
|---|---|---|
| 向量推理是 CPU | 0.25 s/条（批量） | 换 GPU 机器，或改云端 API |
| worker 单线程 | 一次只处理一篇 | `WORKER_CONCURRENCY` 调大（注意别把 embed 打满） |
| 每次问答实时检索 | 无缓存 | 高频重复问题可加缓存层 |

## 七、变更管理

### 上线前必做

1. 备份（第三节）
2. 在独立目录验证过恢复
3. 记录本次变更内容与影响面

### 变更类型与风险

| 变更 | 风险 | 回滚方式 |
|---|---|---|
| 改 `.env` 参数 | 低 | 改回去 + 重启 |
| 改检索参数（阈值等） | 中（影响拒答行为） | 改回去 + 重启 |
| 改权限 SQL | **高**（可能越权） | `git revert` + 重启，**必须重跑权限验收** |
| 加迁移 | 中（可能锁表） | 迁移无法自动回滚，需手工 `DROP` |
| 换向量模型 | **高**（全部重算） | 保留旧向量列副本再操作 |

### 禁止操作

- ❌ `docker compose down -v`（删数据卷）
- ❌ 在 `docker compose` 里改卷名（会挂到新空卷，看似数据全丢）
- ❌ 直接编辑数据库结构而不写迁移文件（下次部署会被覆盖）
- ❌ 用 `make up --build` 当热重载（每次重建镜像，慢且会丢 in-flight 任务）
