# embed 服务性能调优：内存触顶与解析耗时归因

日期：2026-11-16
环境：192.168.1.234，`kb-deskpet-embed-1`（jina-embeddings-v3 + jina-reranker-v2，fastembed 0.7.4 / onnxruntime 1.31.1，8 核 CPU，无 GPU）

---

## 一、起因

上传 5 个文件后，其中两份（`02_机房建设方案_V4定稿.md`、`04_智廷机房建设报价清单.xls`）在桌宠界面卡在「解析中」，而库里实际已经 `completed`。同时整批处理耗时约 14 分钟，远超预期。

客户端侧「轮询 5 分钟硬上限」的显示问题已在 `upload.rs` 单独修复（不属本文）。本文只处理服务端「为什么这么慢」。

---

## 二、三层实测

### 2.1 内存：容器贴着 8G 上限跑，分配反复触顶

| 指标 | 调优前 | 调优后 |
|---|---|---|
| `memory.current` | 7.84 GiB | 2.11 GiB |
| anon（真实进程内存） | **7.77 GiB** | **1.93 GiB** |
| `memory.events.max`（触顶次数） | **4938** | **0** |
| 宿主机 swap used | 4 GiB | **0** |
| 宿主机 available | 6 GiB | 12 GiB |

`memory.peak` 正好等于 8GiB limit。ONNX Runtime 的 CPU memory arena 只增不减，把容器吃满后，内核每次分配都要强制回收 —— 这就是「跑着跑着变慢」的机制。

fastembed 0.7.4 原生暴露 `enable_cpu_mem_arena`（`OnnxModel.EXPOSED_SESSION_OPTIONS`），直接关掉即可，无需改库。

### 2.2 线程：镜像里 `OMP_NUM_THREADS=4`，机器有 8 核

fastembed 的 `threads` 参数会落到 `SessionOptions.intra_op_num_threads`。默认 `None` → onnxruntime 自己定，被镜像的 `OMP_NUM_THREADS=4` 压在半数。

12 条真实切片（1208–1564 字）实测：

| threads | batch=2 | batch=4 |
|---|---|---|
| 4 | 5.47 s/条 | 6.06 s/条 |
| **8** | **4.21 s/条** | 4.97 s/条 |

推理期间整机 CPU busy ≈ 90%（8 核基本打满），说明线程已用满、`4.21s/条` 是这台机器的物理下限。

### 2.3 批大小：越大越慢

按长度降序取的 12 条长切片：

| batch | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| s/条（threads=8） | 8.13 | **4.21** | 4.97 | 6.37 |

切块长度不齐时 padding 把短块补到最长块，批越大浪费越多。**batch=2 是最优点**，此前写死的 8 是最差档。

> 注意：`texts` 里的 `t[:8000]` 不是瓶颈，实际切片远短于此。

## 三、改动

`~/kb-embed/app.py`（仓库 `server/embed_service/app.py`）+ `~/kb-embed/docker-compose.yml`：

| 参数 | 原值 | 新值 | 作用 |
|---|---|---|---|
| `EMBED_CPU_ARENA` | 未设（=true） | `0` | 关 ONNX CPU arena，内存只留真实需求 |
| `EMBED_THREADS` | 未设（受 OMP=4 限制） | `8` | intra/inter op 用满 8 核 |
| `EMBED_BATCH` | 硬编码 `8` | `2` | 避开 padding 浪费 |

`/health` 增加 `threads` / `cpu_arena` / `embed_batch` 三个字段，用于确认配置真的生效。

备份：`~/kb-embed/app.py.bak-20261116-1600`、`~/kb-embed/docker-compose.yml.bak-20261116-1615`

### 效果（HTTP 层，真实切片 300–600 字）

| 场景 | 调优前 | 调优后 |
|---|---|---|
| 8 条一批（= WeKnora `BATCH_EMBED_SIZE=8`） | 6.37 s/条 | **4.96 s/条** |
| 真实分布吞吐 | — | **1.5 s/条 = 0.7 段/s** |

整体提升约 22%。**但也只能到这里** —— CPU 已满，调参无法改变量级。

## 四、端到端验证：真正的瓶颈不在 embedding

用一个 78 KB / 2.75 万字的 Markdown 走完整链路（16:30:40 上传）：

| 阶段 | 起止 | 耗时 | 占比 |
|---|---|---|---|
| 解析 + 切片 + **向量化** | 16:30:40 → 16:32:59 | **2 分 19 秒** | 32% |
| **finalizing（整理中）** | 16:32:59 → 16:37:52 | **4 分 53 秒** | **68%** |
| 合计 | | 7 分 12 秒 | |

135 个切片在 139 秒内完成向量化（1.03 s/段，比压测还快），说明第三节的调优生效了。

finalizing 阶段在做什么（`knowledge_post_process.go`）：

- 1 个摘要任务（`document_summary`，一次 LLM 调用，约 2.5 秒）
- **6 个问题生成批次，共 120 个 chunk**（`question_generation`）—— 每个 chunk 一次远程 LLM 调用
- LLM 模型：`agnes-3.0-flash`，prompt≈895 tokens、completion≈50 tokens/次，单次 1–2 秒

日志中 `[LLM Usage] purpose=question_generation` 连续刷了上百行，这就是 4 分 53 秒的来源。**它与 embed 服务无关，关闭本地模型也压不下来。**

## 五、结论与可选后续

已完成的三项是纯收益、零风险，且解决了「内存触顶导致越跑越慢」的根因。

若还要继续压缩上传后的等待时间，选项按性价比排序：

| 方案 | 预期收益 | 代价 |
|---|---|---|
| 关闭/降低 question generation | finalizing 4′53″ → 接近 0（本次样本 68% 的时间） | 关键词式提问的召回率下降；需在 WeKnora 知识库或系统配置里关 |
| LLM 换更快模型 / 并发调用 | finalizing 压到 1–2 分钟 | 依赖外部 LLM 服务，受网络与配额影响 |
| int8 动态量化 jina-v3 | embedding 再快 2–3 倍（2′19″ → ~1′） | 模型需重新导出；**已入库向量与新向量分布不一致，必须全量重算**；检索精度需回归 |
| 换 `jina-embeddings-v2-base-zh`（768 维，0.64G） | embedding 快 3–4 倍 | 维度不符 DDL 的 1024，需改表 + 重建全部向量 + 重评检索效果 |
| 加 GPU | 数量级提升 | 这台是 QEMU 虚拟机（`Device 1234:1111`），无 GPU 可加 |

**建议**：先评估 question generation 是否可关 —— 它是当前单笔最大开销，且不涉及模型与索引变更。
