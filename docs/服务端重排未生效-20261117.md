# 服务端重排（rerank）从未运行 —— 排查与修复

日期：2026-11-17
影响：所有普通知识问答（`/knowledge-chat/{session}`）的引用排序
状态：已修复上线（镜像 `weknora-app:v0.9.0-rerankfix2`）

## 一、现象

问「02_机房建设方案_V4定稿.md 的完整内容」，答案引用的前 6 个文件全是别的库的模板文档
（`storyboard-template.md`、`prototype-v70-*.html`、`SKILL_副本.md`），目标文档排第 8 位。

桌宠前端 v0.8.28 已经按「答案覆盖率」过滤噪声，但那是兜底——召回榜本身是错的。

## 二、根因

`internal/application/service/session_knowledge_qa.go` 构造 `PipelineRequest` 时设了
`RerankTopK`、`RerankThreshold`，**唯独没设 `RerankModelID`**：

```go
RerankTopK:      s.cfg.Conversation.RerankTopK,
RerankThreshold: s.cfg.Conversation.RerankThreshold,
ChatModelID:     chatModelID,
```

`chat_pipeline/rerank.go` 的第一道判断就是：

```go
if chatManage.RerankModelID == "" {
    diag.Outcome = types.RerankOutcomeNoModel
    pipelineWarn(ctx, "Rerank", "skip", map[string]interface{}{"reason": "empty_model_id"})
    return next()
}
```

于是每次问答都跳过重排，`Merge` 阶段跟着走 `fallback: empty_rerank_result`，
最终引用顺序 = 向量原始分顺序。日志证据（修复前，2026-11-16 全天 39 次请求）：

```
WARNING stage=Rerank action=skip reason="empty_model_id"
WARNING stage=Merge action=fallback reason="empty_rerank_result"
```

`config.yaml` 里的 `enable_rerank: true` 对这条链路是死配置。

对比另外两条链路：检索 API（`knowledgebase_search_rerank.go` 的
`resolveRerankModelID`）和 agent（`session_agent_qa.go:185` +
`pickWorkspaceRerankModelID`）都会解析重排模型，只有最常用的问答入口漏了。
这是上游 v0.9.0 的问题，不是本部署的配置错误。

### 为什么排序会错

重排缺失时排序完全由向量分决定，而向量分对「模板类文档」有系统性偏好：
`SKILL_副本.md` 0.8746 > 机房方案 0.70。技术部门库开了 parent-child（父片 4096），
召回的是整节大块；机房库是 512 字密切片，召回的是 300–800 字节碎片。
同一次排序里「大块顺带命中」压过「小碎片精确命中」。

反证：用日志里的真实改写查询直连 pgvector 算余弦，12/12 全是机房文档
（0.70–0.81），无关文档一个都不进榜。所以召回没问题，坏在融合后没有重排。

## 三、修复

补丁：`deploy/patches/weknora-v0.9.0-rerank-model.patch`（4 个文件）

1. **`session_qa_helpers.go`**：新增 `resolveRerankModelIDForQA`。
   顺序：agent 自己配的 > 租户 `RetrievalConfig` > 工作区内置 rerank 模型
   （`repo.List` 的条件是 `tenant_id = ? OR is_builtin = true`，所以内置模型
   `builtin-rerank-jina` 在任何租户下都可见）。解析不到返回空串，
   退回检索顺序，与修复前行为一致，不会因缺模型报错。
2. **`session_knowledge_qa.go`**：`PipelineRequest` 加
   `RerankModelID: s.resolveRerankModelIDForQA(ctx, req)`。
3. **`chat_pipeline/rerank.go`**：`MaxCandidates` 从
   `max(DefaultMaxCandidates=200, RerankTopK)` 改为
   `max(RerankTopK, LocalMaxCandidates=60)`。上游默认 200 是按云端重排 API
   （批量、毫秒级）定的；本地 fastembed/ONNX 是单实例串行，200 条要 45s。
4. **`internal/reranking/rerank.go`**：新增常量 `LocalMaxCandidates = 60` 及说明。

配套（不属于 WeKnora 源码）：`server/embed_service/app.py` 把送进 cross-encoder
的候选文本从 2000 字截到 **400 字**。

## 四、性能实测（服务器 8 核 Xeon E5-2680 v4，jina-reranker-v2 CPU）

| 场景 | 耗时 |
|---|---|
| 60 条候选，不截断（平均 396 字，最长 1200） | 45.1s |
| 60 条候选，截断 400 字 | **13.2s**（快 3.4 倍） |
| 截断后排序变化 | top10 重合 9/10，第 1、2 名互换（0.5995 / 0.5939，差 0.006） |
| 实际线上（29 候选，全库 11 个 target） | 重排阶段 6.7s，整轮问答 13–16s |

单对约 210ms。候选池设 60 是「覆盖度 vs 等待时间」的折中：实测目标文档在向量榜
排第 8，前 60 名足够覆盖。

阈值 `rerank_threshold: 0.2` 保留：模型输出是 sigmoid 后的 0–1 分数，
无关文档实测 0.10、相关 0.38–0.75，0.2 能分开且有降级逻辑
（`degradeFloor` 0.3 / `degradeFactor` 0.7）。

## 五、构建（重要：不能在宿主机编）

宿主机是 Ubuntu 24.04（glibc 2.39），运行时镜像是 `debian:12.12-slim`（glibc 2.36）。
在宿主机编出来的二进制在容器里会直接报：

```
./WeKnora: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found
```

必须在与运行时同底的容器里编：

```bash
docker run -d --name weknora-builder \
  -v /home/demo/weknora:/src -v /home/demo/gocache:/go \
  -v /home/demo/gocache/build-cache:/root/.cache/go-build \
  -w /src golang:1.26-bookworm sleep infinity

docker exec weknora-builder bash -c 'apt-get update -qq && apt-get install -y -qq libsqlite3-dev pkg-config'
docker exec -e RUSTUP_DIST_SERVER=https://rsproxy.cn -e RUSTUP_UPDATE_ROOT=https://rsproxy.cn/rustup \
  weknora-builder bash -c 'curl -sSf https://rsproxy.cn/rustup-init.sh | sh -s -- -y --profile minimal --default-toolchain stable'

# anydoc 静态库（31MB Rust 产物，需 -C embed-bitcode=no，否则 cgo 报
# disallowed LTO section ".llvmbc"；若已生成，用 objcopy 剥掉也行）
docker exec -e PATH=/root/.cargo/bin:/usr/local/go/bin:/usr/bin:/bin \
  -e CARGO_PROFILE_RELEASE_LTO=false -e RUSTFLAGS='-C embed-bitcode=no' \
  weknora-builder bash -c 'cd /src && ./scripts/build-anydoc-lib.sh'

# 兜底：objcopy --remove-section=.llvmbc --remove-section=.llvmcmd <lib.a> <新.a>
# 本次最终用的是 objcopy 这条路（RUSTFLAGS 未生效，llvmbc 段仍在 304 处）

docker exec -e PATH=/usr/local/go/bin:/usr/bin:/bin \
  -e GOPROXY=https://goproxy.cn,direct -e GOSUMDB=off -e GOTOOLCHAIN=local \
  weknora-builder bash -c 'cd /src && CGO_ENABLED=1 go build -tags anydoc \
  -ldflags="-w -s -X github.com/Tencent/WeKnora/internal/handler.Version=v0.9.0-rerankfix \
  -X github.com/Tencent/WeKnora/internal/handler.Edition=standard" \
  -o /src/WeKnora-glibc236 ./cmd/server'

docker build -f deploy/patches/Dockerfile.weknora-rerankfix -t weknora-app:v0.9.0-rerankfix2 .
```

Dockerfile 只换二进制，其余层（duckdb 扩展、entrypoint、appuser、libsqlite3-0）沿用官方镜像：

```dockerfile
FROM wechatopenai/weknora-app:v0.9.0
COPY WeKnora-final /app/WeKnora
```

`docker-compose.override.yml` 里加一行 `image: weknora-app:v0.9.0-rerankfix2`，
然后 `docker compose up -d app`。

## 八、升级注意

**升级到任何新版本镜像都会丢掉这几处改动。** 重放步骤：

1. `git apply`-style 手工套 `deploy/patches/weknora-v0.9.0-rerank-model.patch`
   （路径带前缀，用 `patch -p0` 或按 hunk 手工改）
2. 按第五节重新编译（新版本可能改 `go.mod` 的 Go 版本要求，容器镜像要跟着换）
3. 重打镜像、改 override 的 tag、`docker compose up -d app`

如果上游在新版本里修了这个问题（`RerankModelID` 被赋值），第 1 步可跳过，
只需验证日志里出现 `rerank_model=` 即可。
