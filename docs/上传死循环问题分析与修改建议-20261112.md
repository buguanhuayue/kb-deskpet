# 上传队列「一直上传中」死循环 —— 问题分析与修改建议

- 日期：2026-11-12
- 现象反馈人：李高峰（桌宠登录账号 ligaofeng）
- 出问题客户端：`192.168.1.203`（macOS），应用版本 v0.8.22（CI Release 产物，编译时间 2026-11-11 14:23）
- 服务端：192.168.1.234，域名 `knowledge.xinyeonline.com.cn` → `WeKnora-frontend`(nginx, 9527) → `WeKnora-app`(18080)
- 结论一句话：**批量拖拽上传时，第 4 个文件在服务端已成功入库，客户端却把后续每一次重发都当成「可重试错误」，在一条 keep-alive 连接上以约 7 次/秒无限重传同一文件；因为上传队列是串行（head-of-line）模型，这一条卡死直接冻结了后面 11 个文件。**

## 一、现象

面板上传队列停在 `3/15`：

```
20261112113922.jpg   已入库
20261112111730.jpg   已入库
20261112111549.jpg   已入库
20261112111541.jpg   上传中   ← 卡死，17:20 与 17:44 两次截图状态一致
20261112110949.jpg   排队中
20261112104301.jpg   排队中
...（共 15 项）
```

会话里还出现过汇总播报：`「技术部门知识库」上传结果：成功 3 项、1 项库里已有、7 项仍在解析或排队`。

## 二、服务端实测证据（决定性）

全部来自 `WeKnora-app` 与 `WeKnora-frontend` 的访问日志 + 现场抓包。

### 2.1 时间线（本地时间）

| 时间 | 事件 |
|---|---|
| 17:18:15.770 | POST knowledge/file → **200**（响应 845B，文件 20261112113922.jpg） |
| 17:18:16.104 | POST → **200**（844B） |
| 17:18:16.322 | POST → **200**（844B） |
| 17:18:16.560 | POST → **200**（845B，文件 20261112111541.jpg，创建记录 `17a08b6c-…`） |
| 17:18:16.6 起 | 同一个文件开始 **409 duplicate_file**，此后**不再有任何 200** |
| 17:19:01 | 该记录 `parse_status=completed`，服务端解析已经完成 |
| 17:18 – 17:26 | 409 累计约 2900 次 |
| 17:44 – 17:46 | 仍在继续（2 分钟 776 次） |
| 17:55 | 单文件 409 累计 **4207 次**，单条连接持续复用 |

四个 200 的间隔是 230–320ms，正好对应 `kick()` 串行取下一个条目的节奏；之后的 409 间隔 125–130ms（约 7–8 次/秒），**没有任何退避**。

### 2.2 请求归属（排除第三方）

现场 tcpdump（服务器 9527 对外端口）抓到的请求头：

```
POST /api/v1/knowledge-bases/9efc0043-…/knowledge/file HTTP/1.1
Accept: application/json
Accept-Encoding: gzip
Connection: keep-alive
（无 User-Agent）
```

- 无 User-Agent → reqwest（Rust）或 undici（Node）这类客户端；浏览器一定带 `Mozilla/5.0…`
- `Accept: application/json` → 与 `upload.rs::upload_one` 中 `.header("Accept", "application/json")` 完全一致
- 同机还并发着 webview UA 的 `/knowledge-bases` 请求，可确认该机器上跑的就是桌宠

结论：**循环请求就是桌宠的 Rust 上传客户端发出的，不是浏览器、不是同事脚本。**

### 2.3 影响面

- 无效上传流量：716,726 B × 4207 ≈ **2.9 GB**（内网/公网带宽 + 服务端 nginx 每次把 body 缓冲到临时文件）
- 队列被头阻塞：15 个文件只发出 4 个，其余 11 个永远「排队中」
- 用户侧完全无法自愈：UI 只有「移除」，没有取消/超时提示；重启应用才会停（队列在内存里，重启即清）

## 三、代码定位

涉及文件：`tauri-app/src-tauri/src/upload.rs`

### 3.1 上传状态机

```
kick()                   974-1011   单飞 worker，loop 里 pick_next → upload_one
  └ pick_next()          959-967    只取 status == "queued" 的第一条
upload_one()             585-830    单条上传：uploading → POST → parsing → poll_parse → done
  └ 内层 loop            669-785    ★ 重发循环，本 bug 的发生地
     ├ 网络错误重试       708-720    network_retries < 1 才 continue（有界）
     ├ 401 重放           726-747    retried_401 只允许一次（有界）
     ├ 413                748-751    fail 终态
     ├ 409 duplicate_file 752-768    exists 终态，return
     └ !is_success        769-783    fail 终态
```

从源码看，**409 这条分支是终态**（标记 `exists`、`progress=100`、`knowledge_id=kid`，然后 return），后续 `kick` 应继续取第 5 条。也就是说：**仓库里任何一个已提交版本（v0.8.15 起该分支就存在，三次改动都没删过）都不应在 409 上自旋。**

### 3.2 与实测行为的冲突

实测是「409 → 立刻重发同一条」，而且回到 `uploading` 状态反复 POST。这与上面的状态机不符，只有三种可能：

1. **线上二进制的这段逻辑与 tag 源码不一致**
2. **409 判定失效**，且同时命中了某条 `continue` 路径
3. 同一条目被外部反复重置为 `queued`（`upload_retry`），但 UI 从未出现「失败」态，且 7 次/秒的人工点击不可能，已排除

### 3.3 对二进制做的取证（有结论但不能单独定罪）

本机 `/Applications/知识小助.app`（0.8.22，mtime 2026-11-11 14:26，与 Actions 构建时间 06:23Z 吻合）直接扫二进制：

| 字面量 | 出现次数 | 说明 |
|---|---|---|
| `续期后仍被拒绝` | 1 | v0.8.22 新增（仅 4ec6347 引入）→ 二进制确实是 0.8.22 |
| `这是文件夹` / `文件是空的或读不到` / `构造请求失败` / `超过服务端` / `没有选择知识库` / `队列太长` | 各 1 | 与 HEAD 一致 |
| `上传没有完成` | 0 | 该文案在 4ec6347 已被删除 → 与 HEAD 一致 |
| **`duplicate_file`** | **0** | ⚠️ 唯一缺失的关键字面量 |

`duplicate_file` 是 14 字节 `Some("duplicate_file")` 比较的字面量。**注意**：LLVM 对短字符串等值比较有可能内联成 8 字节立即数比较，那样字面量就不会以连续字节出现在 rodata，所以「搜不到」还不能直接判定「分支不存在」。**这一条必须靠重新构建 + 反汇编比对来闭环，不能当结论用。**

### 3.4 为什么「409 判定失效」本身也不足以解释死循环

如果只是 `v.get("code")` 取不到（比如网关把 409 换成了 HTML 错误页、或 `resp.text()` 失败被 `unwrap_or_default()` 吞成空串），代码会落到 `!status.is_success()` → `fail()` → **终态**，UI 应显示「失败」而不是「上传中」。所以还必须有另一条把它送回 `continue` 的路径。最可疑的是 708–720 的**网络层重试**：服务端处理完请求后如果连接提前半关（keep-alive 复用 + nginx body 落临时文件 + 早退 409），`reqwest::send()` 可能返回 `Err` 而不是 409 响应。此时 `network_retries < 1` → `continue` 重发。但这个分支**只允许重试一次**，仍然解释不了 4000 次。

⟹ 综合判断：**线上二进制里 409 之后的行为不是「exists/fail 二选一终态」**。最可能是构建产物与 tag 源码存在差异，其次是某个我们尚未看到的运行期分支。这一点必须用 3.3 的重构建比对来闭环。

## 四、真正需要修的缺陷（无论根因落在哪一条）

即使根因最终是「二进制与源码不一致」，下面这些问题也是**真实存在、且是这次事故放大器**的，必须一起改：

### P0-1 单条上传缺少「总尝试上限 + 退避」

`upload_one` 内层的 `loop` 依赖**每个 `continue` 分支各自维护计数器**（`network_retries`、`retried_401`）。这种写法只要将来任何一个分支漏掉计数器、或者新增一条 `continue`，就变成无限重发，且没有任何兜底。

建议：外层加硬上限，与具体分支解耦。

```rust
const MAX_ATTEMPTS: usize = 3;
for attempt in 0..MAX_ATTEMPTS {
    ... send ...
    match 结果 {
        Ok(resp) => { 处理状态码（409/413/401/其它）; break/return; }
        Err(e) if attempt + 1 < MAX_ATTEMPTS => {
            sleep(400ms * 2u32.pow(attempt as u32)).await;   // 400 / 800
            continue;
        }
        Err(e) => { fail(...); return; }
    }
}
fail(&app, &id, "重试 3 次仍未成功");   // 兜底终态，保证 kick 一定能前进
```

### P0-2 409 的判定不应依赖响应体

现在 `v.get("code") == Some("duplicate_file")` 是唯一入口，判定链路上任何一个环节（反代改错误页、body 被截断、gzip 解压异常、字段改名）都会让它失效。而 409 语义上就是「冲突，重试无意义」。

建议：**先看 status，再拿 body 做增强**。

```rust
if status == reqwest::StatusCode::CONFLICT {
    let kid = v.pointer("/data/id").and_then(|x| x.as_str()).unwrap_or("").to_string();
    update_item(&app, &id, |it| {
        it.status = "exists".into();
        it.progress = 100;
        it.knowledge_id = kid;          // 拿不到就留空，UI 显示「已存在」不带移除按钮
        it.parse_status = "completed".into();
    });
    return;
}
```

### P0-3 `kick()` 缺「无进展熔断」

`kick` 的循环只判断「还有没有 queued」，不检查「这一轮有没有真的推进」。一条卡住 = 整批停摆，且没有任何自愈。

建议：worker 里记录 `last_id` / `last_status`，同一 id 连续 2 次以上仍是 `queued|uploading` → 强制标 `failed`（错误信息「该文件上传卡住，已跳过」）并继续下一条。

### P0-4 单条上传没有独立超时

全局 `client()` 的 `timeout(600s)` 是整条请求的超时，一条卡住最坏要 10 分钟才释放，期间整批不动。建议用 `tokio::time::timeout(Duration::from_secs(90), send())` 包住单次请求，超时按失败处理，保证批量上传的推进性。

### P1-1 队列只在内存，无持久化

重启即清空（本次止血靠的就是这一点），但用户视角是「我那 15 个文件白排了」。建议把 `items` 落到 `tauri-plugin-store`，冷启动读回 `queued/failed` 继续跑，并把上次 `uploading` 的条目降级为 `failed（上次未完成）`。

### P1-2 UI 缺「卡住」的可见性

`uploading` 状态没有看门狗：30 秒无进展应提示「可能卡住，可重试或取消」，并给该条一个「取消」按钮（现在只有 `failed` 才有「重试」，`uploading` 只能整条「移除」）。

### P1-3 Rust 侧零日志

整个上传链路没有一行日志落盘，本次只能靠服务器反向推断（耗时主要花在这里）。建议每次状态迁移 + 每次 request attempt 打一行到 `~/Library/Logs/com.company.deskpet/upload.log`（滚动保留 7 天）。这是排查这类问题的**最低成本设施**。

### P2-1 服务端兜底限流

nginx 对 `/api/v1/knowledge-bases/*/knowledge/file` 加 `limit_req zone=upload burst=10 nodelay`，把客户端 bug 的影响限制在服务端侧（本次 4200 次请求就是完全裸奔进来的）。

### P2-2 双窗口拖拽会重复暂存（同源隐患）

`tauri-bridge.js:154` 的 `tauri://drag-drop` 是无差别全局监听：拖到桌宠时，panel 走 `stagePathsFromTauri`，pet 又走 `handlePetDropFromTauri` → `stagePathsInPanel`，同一批文件在暂存清单里会出现两份（最终被 `upload_enqueue` 按 path 去重挡住，但属于同一类「批量事件重复触发」隐患）。建议按 `window label` 过滤，只让落点窗口处理。

### 改动清单

### 关键语义

- **`attempts` 落在条目上**，跨 `kick` / 多次 `upload_one` 累加。这是与「函数局部计数器」的本质区别：局部计数器每次重入都会归零，等于没有上限。
- **失败文案给出路**：`已自动重试 3 次仍未成功，请检查网络后手动重试`，配合人工重试配额，用户不会陷入死局。
- **`parsing` 算已推进**：文件已入库，解析由独立轮询任务接管，不占 worker。
- **`upload_retry` 的状态闸**：只允许 failed / done / exists 三类重置，正在跑的条目一律拒绝。

## 八、真因找到了：`uuid_like()` 时钟碰撞（2026-11-13 现场定位）

上面第七节说「直接触发路径无法复现」——**那是没找对地方**。真因不在状态机，在 id 生成。

### 证据

11-13 本机复现批量拖拽（6 个 jpg），日志里出现：**6 个文件只生成了 5 个唯一 id**。
`u_18e7768764f26248…` 同时属于 `20261112103550.jpg` 和 `20261112102750.jpg` 两个不同文件。

实测这台 Mac 的时钟分辨率（`SystemTime::now().as_nanos()` 连续采样 2000 次）：

```
2000 次连续采样 → 126 个唯一值（重复 1874 次）
```

**约 16 微秒才走一格。** 批量入队是 `for` 循环里连续 `UploadItem::new()`，两三次迭代落在同一刻度上几乎必然发生。

### 后果链

`update_item` / `begin_attempt` / `pick_next` 全部用 `items.iter().find(|i| i.id == id)`，**永远只命中第一个同 id 的条目**：

1. **卡在「解析中」**（本次现象）：服务端 09:29:07 已 `completed`，但 `poll_parse` 的 `update_item` 把 done 写到了另一个同 id 条目上，真正那条永远停在 `parsing`。
2. **每秒 7 次 409 死循环**（11-12 事故）：旧版 `upload_one` 不检查状态，每轮都取第一个同 id 条目、重传它已存在的文件 → 409 → 标 exists → 返回；而第二个同 id 条目始终是 `queued`，`kick` 又把它取出来 → 无限循环。**这就是 4207 次重传的真因**，与控制流、二进制一致性都无关。

也就是说：11-12 那份「任何 committed 版本都不可能自旋」的结论只对单条目成立，**同 id 双条目把状态机打成了自指**。

### 修复

| 位置 | 改动 |
|---|---|
| `uuid_like()` | 加进程内原子自增序号 `SEQ`，id = nanos + seq + rand，同一微秒创建也必然不同 |
| `poll_parse()` | 补全链路日志（start / 状态变化 / done / failed / abort / timeout） |
| `poll_parse()` | `server_url` 为空不再静默 `return`，改为标失败 + 落日志（原先会永远卡 parsing 且无痕迹） |

### 验证

- `item_ids_are_unique_in_a_burst`：连续创建 5000 个条目，id 必须全不同
- 时钟采样实验：证实 16µs 分辨率，说明该测试在旧代码下必然失败

### 对 11-12 结论的修正

- 死循环**不是**线上二进制与仓库不一致，**也不是**未知重入路径 —— 是 `uuid_like` 的 id 碰撞，需要「批量拖拽」这个前提才能触发，单文件测试永远复现不出来。
- 第七节的 attempts 上限仍然保留：它把「同 id 双条目」这类未知缺陷的最坏影响压到 12 个请求，是有效的第二道防线。
