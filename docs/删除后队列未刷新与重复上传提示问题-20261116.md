# 「移除后队列没刷新 → 再传提示已存在」问题分析与修改方案

- 日期：2026-11-16
- 提单现象（截图 v0.8.24）：点「移除」并确认「从知识库删除？」，队列条目仍在（仍显示「已入库」），再次拖同一个文件上传，一直提示「文件已存在 / 已在队列或库里」。
- 结论：**桌宠侧队列（Rust `UploadState.items`）与面板侧列表（JS `queueItems`）是两份状态，删除只清了 JS 那份**；同时 WeKnora 的删除是异步任务且从未真正落地，导致重复删除返回 404、条目永远清不掉。两者叠加，才出现「删也删不掉、传也传不进」。

---

## 一、证据链（2026-11-16，client_ip=192.168.1.203，WeKnora-app 日志）

`邓白.rtf`（tenant 10000，kb 9efc0043）：

`虚拟机清单_20261114.md` 更典型：09:54:09 删除成功提交，此后 14:56:43、14:56:47、15:04:29、15:04:32、15:04:54、15:04:56、15:05:56、15:06:17 **连续 8 次 DELETE 全是 404**，用户每点一次「移除」就只能拿到「删除失败」。

数据库侧（`WeKnora-postgres`）：

Redis 侧 asynq 五个队列 pending/active/scheduled/retry/archived **全部为 0**，`task_dead_letters` **0 条** —— 任务被消费了，却什么都没清理。也就是说：`deleted_at` 写了、`parse_status` 停在 `deleting`，清理动作从未执行完，且没有补偿任务。

## 二、根因（三处，按严重度）

### 根因 1（主因）：删除只清了 JS 列表，没清 Rust 队列

`tauri-app/src/public/js/panel.js:2372-2380`

```js
const r = await window.pet.deleteKnowledge(it.knowledgeId)
if (r && r.ok === false) return toast(r.error || '删除失败', 'warn')
queueItems = queueItems.filter((x) => x.id !== it.id)   // 只改了面板内存数组
renderQueue(queueItems)                                  // Rust 侧 items 原封不动
```

队列的唯一真相在 Rust：`src-tauri/src/upload.rs` 的 `UploadState.items`（`upload_list` / `upload_clear` 都读写它）。面板这份 `queueItems` 只是镜像。于是：

- 任何一次 `emit_stats`（`upload.rs:257`，只发 `{stats}` 不带 item）→ 面板 `panel.js:2396` 走「无 item 就 `listUploads()` 全量刷新」→ **被删掉的行原地复活**，还带着已失效的 `knowledgeId`。
- 于是用户看到的是「删除后没刷新」，再点「移除」就是对着一个已经软删的 id 发 DELETE → 404 → 提示删除失败 → 行永远清不掉。

### 根因 2：入队去重把「已完成」也算占位，重传必然被拦

`tauri-app/src-tauri/src/upload.rs:1423`

```rust
if g.items.iter().any(|i| i.path == path && i.status != "failed") {
    exists += 1;
    continue;
}
```

只要队列里还有同一路径的非 failed 条目（`done` / `exists` 都算），就永远返回 `exists`，面板据此播报「另外 N 项已在队列或库里，跳过重复上传」（`panel.js:1888`）。由于根因 1 让那条陈旧条目清不掉，**同一路径就再也传不进去了** —— 这就是「一直提示文件已存在」的直接来源。用户只能靠「清理已完成」或重启应用（队列在内存）绕过，旁证是 15:03:42 那次 200 的成功上传。

### 根因 3：把 404 当失败，删除操作不幂等

`tauri-app/src/public/js/tauri-bridge.js:1090-1097` 只区分 ok / 非 ok，错误体里连 HTTP 状态码都不带（`apiRequest` 抛 `new Error(msg)`，`tauri-bridge.js:390-391`）。

而 WeKnora 的 DELETE 是 **软删 + GORM 默认作用域**（日志里 `WHERE id = $1 AND deleted_at IS NULL`），第一次删除后同一 id 必然 404。语义上「已经不在了」对我们就是成功，现在却报失败并保留队列行，用户只能反复点。

## 三、修改方案（待审核，未改代码）

### A. 桌宠侧（4 处改动，服务端零改动，可独立发版 v0.8.25）

**A1. 打开 `upload_forget` 的取消逻辑**（`src-tauri/src/upload.rs`，新增命令）

```rust
/// 用户在面板点了「移除」并且服务端已接受删除后调用：
/// 把这条（连同同路径的已完成条目）从队列里真正摘掉，避免「删了又回来」。
#[tauri::command]
pub fn upload_forget(app: AppHandle, id: String) -> Value {
    let mut removed = 0usize;
    {
        let st = app.state::<UploadState>();
        let mut g = st.inner.lock().unwrap();
        if let Some(path) = g.items.iter().find(|i| i.id == id).map(|i| i.path.clone()) {
            let before = g.items.len();
            // 只清终态：进行中的条目还在上传，不能因为删了知识就把它掐掉
            g.items.retain(|i| {
                !(i.path == path && matches!(i.status.as_str(), "done" | "exists"))
            });
            removed = before - g.items.len();
        }
    }
    emit_stats(&app); // 两个窗口都会收到，面板按既有分支重新 listUploads
    json!({ "ok": true, "removed": removed })
}
```

**A2. 入队去重只拦「进行中」的条目**（`upload.rs:1423`）

```rust
// 已完成/已存在的条目不再阻止重新上传：库里那份可能刚被删掉，
// 客户端无从判断，交给服务端按 file_hash 判定（命中就 409 → exists，语义准确）。
// 同路径的旧终态条目直接替换，保证一条路径只有一行。
if g.items.iter().any(|i| {
    i.path == path && matches!(i.status.as_str(), "queued" | "uploading" | "parsing")
}) {
    exists += 1;
    continue;
}
g.items.retain(|i| !(i.path == path && matches!(i.status.as_str(), "done" | "exists")));
```

> 注：`panel.js:2393` 的 `onUploadUpdate` 本来就是「先按 id、再按 path 合并」，替换语义与前端一致，不会画成两行。

**A3. 错误对象带上状态码，删除按幂等处理**（`tauri-bridge.js`）

```js
// apiRequest 抛错处（约 390 行）
const err = new Error(msg);
err.status = res.status;                 // 新增
err.code = json?.error?.code;            // 新增（WeKnora 的 1003 等业务码）
throw err;

// deleteKnowledge（1090 行）
deleteKnowledge: async (id) => {
  try {
    await apiRequest(`/knowledge/${encodeURIComponent(id)}`, { method: 'DELETE' });
    return { ok: true };
  } catch (e) {
    // 已经不存在（重复删除 / 异步任务已把行删掉）按成功处理：
    // 用户的意图「让它从库里消失」已经达成，不能因为 404 就卡住队列。
    if (e.status === 404 || e.code === 1003) return { ok: true, alreadyGone: true };
    return { ok: false, error: e.message, status: e.status };
  }
},
forgetUpload: async (id) => {
  if (!IS_TAURI) return { ok: true };
  return (await invoke('upload_forget', { id })) || { ok: true };
},
```

**A4. 面板删除流程收口**（`panel.js:2372-2380`）

```js
const ok = await confirmBox('从知识库删除？', `「${it.rel || it.name}」会从库里删掉，同事将搜不到它。`, '删除')
if (!ok) return
const r = await window.pet.deleteKnowledge(it.knowledgeId)
if (r && r.ok === false) return toast(r.error || '删除失败', 'warn')
await window.pet.forgetUpload(it.id)          // 新增：让 Rust 侧也忘掉这条
queueItems = await window.pet.listUploads()   // 以 Rust 为准回填，不再自己 filter
renderQueue(queueItems)
toast(r?.alreadyGone ? '库里已经没有它了，已从队列移除' : '已删除')
```

**A5（可选，建议做）**：`exists` 状态的条目也带「移除」按钮（`panel.js:2367` 目前 `it.knowledgeId` 为真就显示）。此时提示文案应改成「库里已存在的这一篇会被删掉」，避免用户以为在清自己的列表。

### B. WeKnora 服务端

> 结论先行：**升级解决不了**。`v0.9.0` 与 upstream `main` 的 `internal/application/service/knowledge_delete.go`
> 逐行 diff 为 0 行差异 —— 软删是刻意设计（源码注释原话：*the knowledge row (being soft-deleted right now
> by the caller)*），上游既没有回收器，也没有把「删不存在的知识」当成幂等成功。所以服务端只做两件事：
> 运维侧补幂等（由客户端兜底，见 A3）+ 回收存量垃圾（见下）。

1. **删除链路真相（已逐行核对源码 + 线上日志）**：
   `DELETE → 入 asynq 任务 → Marked 1 knowledge entries as deleting → 删 5 条向量索引 → 删物理文件
   → repo.DeleteKnowledgeList（GORM 软删）→ 打 "Successfully deleted 1 knowledge items"`。
   任务本身是**成功**的（所以 asynq 零积压、死信 0），留下的是软删行 + `parse_status='deleting'` 永久不收敛。
2. **数据回收脚本**：`deploy/purge-soft-deleted.sh`（默认 dry-run，`--apply` 才落盘）。
   先 `BEGIN` 建临时表圈定目标，再按 向量 → 图片/修订/标签/记忆亲和 → 切片 → 处理跨度 → 知识行 的顺序硬删，
   最后顺手清「知识行早就没了」的孤儿向量/切片；干跑时事务以 `ROLLBACK` 收尾。
3. **定时化**：服务器 `demo` 用户 crontab 每天 04:17 跑一次 `--apply`，日志 `~/purge-soft-deleted.log`。
4. **风险点已实测定性**（详见第六节）：残留切片**不会**导致内容泄漏，检索侧按 knowledge 做了兜底过滤。

## 六、「删掉的文档还能被搜到吗」——实测结论：不能

这是本次唯一真正会伤到人的风险，按「数据层 → 接口层」两段验证：

**① 数据层确实会召回。** 用应用日志里那条真实检索 SQL 直接打库（ParadeDB 全文）：
已软删的 `差旅报销管理办法.md` 对查询「报销」得分 7.56，排第 1；
`桌宠测试.md`（软删，但它的 chunk 和 embedding 都没被标记删除，是**最坏情况**）对「相对路径 测试文档」
得分 29.59，**以 3 倍分差排第 1**。

**② 接口层把它过滤掉了。** 用真实账号（`ligaofeng`，租户 10016，技术部门知识库 9efc0043）
在 `/api/v1/knowledge-chat` 上端到端提问两次：

| 提问 | 引用文档 | 回答 |
|---|---|---|
| 差旅报销的住宿标准是多少？ | 17-桌宠使用说明.md、知识小助桌宠使用说明.pptx 等 17 条，**无已删文档** | 「资料里没有…」 |
| 那份验证桌宠相对路径上传功能的测试文档说了什么？ | 同上，**无 桌宠测试.md** | 「在提供的资料中，没有找到…」 |

即：召回集里有它，但组装引用/上下文时按 knowledge 侧过滤掉了，模型根本没看到内容。
**「同事将搜不到它」这句承诺是成立的**，残留数据只是存储垃圾，不构成泄漏。

> 附带结论：`embeddings` 检索 SQL 本身不带 `deleted_at` 过滤，所以这个安全性完全依赖上游的
> 后置过滤。如果哪天上游改动这一步，风险会立刻回来 —— 保持每天回收软删数据，就等于把这个依赖
> 缩短到 24 小时以内。
